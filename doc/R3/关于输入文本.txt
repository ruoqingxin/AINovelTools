一、不要让“写作 AI”直接面对全部项目资料

附加标准：前端展示 UI 固化标准
- 前端展示 UI 在不影响性能的前提下，必须美观、清晰、易用。
- 首次实现功能时确定布局、信息层级、视觉规范、控件规范、完整状态和响应式行为，形成稳定基线。
- 后续功能优先复用既有 UI；除非有明确的可用性、性能或业务依据，不进行大规模改版。
- UI 调整须保持操作路径和数据语义连续，并完成桌面与窄屏检查。
建议把系统分成两个角色。

1. 上下文准备者
负责：

理解本章需要什么资料
检索相关人物、地点、事件和设定
压缩前文
识别冲突和缺失
按优先级整理材料
生成“章节写作包”
它可以由：

确定性程序
检索系统
专门的上下文规划 AI
共同完成。

2. 正文写作者
只负责：

阅读整理好的章节写作包
根据章节目标生成正文
报告发现的冲突或信息缺失
不自行翻阅整个项目
不自行决定哪个版本的资料有效
也就是说：

*.txt
Plaintext
完整项目资料
    ↓
检索、筛选、压缩、排序
    ↓
章节写作包
    ↓
正文写作 AI
    ↓
章节草稿
二、完整资料和 AI 输入要分开
系统内部可以保存非常完整的内容：

世界观资料
人物档案
全部正文
时间线
地点设定
势力关系
伏笔
文风要求
写作技巧
历史修改记录
但 AI 每次只接收和当前任务有关的部分。

可以将资料分成三种记忆。

1. 长期知识库
保存完整事实：

世界观
人物完整档案
地点
道具
势力
历史事件
全部章节
写作规范
这里负责“保存完整”，不直接全部输入模型。

2. 项目状态记忆
保存故事发展到当前时刻的状态：

当前时间
人物在哪里
人物知道什么
人物不知道什么
人物关系变化
持有什么物品
受了什么伤
哪些事件已经发生
哪些伏笔已经埋下
它回答的是：

故事写到现在，各项事物目前是什么状态？

3. 当前工作记忆
也就是本次调用真正交给 AI 的内容：

当前章节目标
本章人物状态
本章相关设定
前一章衔接
必须处理的伏笔
本章风格和写作要求
三、章节写作包应该包含什么
建议分成以下七层。

第一层：本章任务合同
这是本次写作最核心的信息。

*.yml
YAML
chapter:
  id: chapter_012
  title: 暂定标题
  viewpoint: 林越
  time: 大陆历317年冬月初三夜
  location: 北城客栈
  target_length: 4000
  main_goal: 林越潜入客栈寻找密信
  ending_requirement: 林越发现密信已经被人取走
还要包含：

本章开场状态
本章结束状态
必须发生什么
不能发生什么
哪些内容可以自由发挥
第二层：章节节拍或场景纲要
不要只给一句“写潜入客栈”。

应该拆成场景节拍：

*.yml
YAML
beats:
  - id: beat_01
    goal: 林越观察客栈外围
    conflict: 城防巡逻比预期更严
    result: 找到后院入口
  - id: beat_02
    goal: 进入二楼目标房间
    conflict: 房间内有人提前搜查
    result: 林越躲到横梁上
  - id: beat_03
    goal: 获取密信
    conflict: 密信已经被取走
    result: 发现留下的半枚蜡印
这样 AI 知道故事应该如何推进，而不是依靠背景资料猜测。

第三层：当前状态快照
人物完整档案可能有上万字，但这一章只需要当前状态。

*.yml
YAML
characters:
  - id: lin_yue
    role_in_chapter: 视角人物
    current_goal: 找到能够证明知府通敌的密信
    emotional_state: 谨慎、焦虑，但表面冷静
    physical_state: 左肩轻伤，不能长时间用力
    current_knowledge:
      - 知道密信藏在天字三号房
      - 知道客栈老板与知府有关
    unknown_information:
      - 不知道沈青已经拿走密信
      - 不知道巡逻队长认识自己
    relationship_state:
      shen_qing: 怀疑但尚未敌对
关键不是“林越一生的全部经历”，而是：

林越在这一章开始时，处于什么状态。

这可以避免 AI 让人物提前知道不该知道的事。

第四层：相关背景知识
背景知识要按“本章相关性”检索，不能整本输入。

例如本章发生在客栈，只需要：

*.yml
YAML
relevant_canon:
  - source: location_beicheng_inn
    fact: 客栈共有三层，后院通往厨房和马厩
  - source: city_curfew_rule
    fact: 入夜后每半个时辰有一支巡逻队经过
  - source: secret_letter_setting
    fact: 密信使用黑色火漆，印章是双尾蛇
不需要输入：

南方帝国完整历史
几百年前的战争
本章没有出现的人物完整档案
与客栈无关的地点资料
除非它们确实会影响本章。

第五层：前文衔接信息
前文不能简单粗暴地全部输入。

建议使用“距离越近，保留越详细”的策略。

与当前章节距离	输入方式
前一章结尾	保留原文或详细内容
前1—3章	详细章节摘要
本卷较早章节	事件摘要和未解决事项
以前各卷	卷摘要和相关事实检索
很久以前的细节	需要时检索原文
例如：

*.yml
YAML
continuity:
  previous_chapter_ending:
    type: original_excerpt
    content: 前一章最后若干段原文
  recent_events:
    - 第10章：林越从账房口中得知密信存在
    - 第11章：林越跟踪送信人来到北城客栈
  unresolved_threads:
    - 巡逻队长曾在第7章见过林越
    - 沈青正在秘密调查同一封密信
一般来说，真正需要保留原文的是：

上一章结尾
与本章直接呼应的原始段落
必须延续语气的对话
需要回收的伏笔原文
其余内容可以使用结构化摘要。

第六层：风格包
不要把几十万字范文全部塞进去。

应该将风格拆成两部分。

风格规则卡
*.yml
YAML
style:
  narrative:
    person: 第三人称
    viewpoint: 限知视角
    distance: 贴近人物感受，但避免大段心理解释
  prose:
    sentence_rhythm: 紧张场景以短句为主
    description_density: 中等
    dialogue_ratio: 低
    metaphor_density: 低
  tone:
    - 克制
    - 冷峻
    - 有压迫感
  avoid:
    - 网络化表达
    - 现代词汇
    - 上帝视角信息
    - 连续堆砌形容词
    - 直接解释人物全部情绪
少量风格样例
提供一到三个最有代表性的短片段，用来展示：

句式节奏
描写密度
对话方式
心理描写方式
场景转换方式
风格卡负责“明确规则”，样例负责“让 AI 感受实际效果”。

只给样例、不总结规则，AI 容易模仿表面词汇；只给规则、不提供样例，AI 又可能理解偏差。

第七层：本章启用的写作技巧
不需要把整本《写作技巧大全》输入 AI。

应根据章节类型，只启用当前需要的技巧。

例如这是潜入章节：

*.yml
YAML
active_techniques:
  - name: 信息延迟
    requirement: 不要立刻说明房间内的人是谁
  - name: 感官聚焦
    requirement: 优先使用声音、阴影和触觉塑造紧张感
  - name: 障碍升级
    requirement: 每个场景的风险高于上一场景
  - name: 结尾悬念
    requirement: 最后揭示密信被取走，但不揭示取走者
而不相关的技巧，例如大规模战争描写、爱情对话技巧，本章不需要输入。

四、资料要建立压缩层级
同一份信息应该允许存在不同精度版本。

以章节为例：

*.txt
Plaintext
L0：章节完整原文
L1：章节详细摘要
L2：章节事件列表
L3：人物状态变更
L4：一句话章节摘要
L5：卷级摘要
系统根据任务决定使用哪一层。

例如要写第十二章：

*.txt
Plaintext
第11章：原文结尾 + 详细摘要
第9—10章：事件列表
第1—8章：相关人物和伏笔检索
前一卷：卷摘要
人物资料也可以分层：

*.txt
Plaintext
L0：完整人物档案
L1：人物核心设定卡
L2：当前状态卡
L3：本章角色卡
正文写作时，主要使用“本章角色卡”；发现信息不足时，再向上检索。

五、建立明确的上下文优先级
资料一多，最危险的是互相矛盾。

因此每个上下文包都要声明优先级。

*.txt
Plaintext
P0：用户本次明确指令
P1：已批准的正式设定
P2：已批准的章节纲要
P3：故事当前状态快照
P4：前文正式正文
P5：风格规范
P6：参考样例
P7：AI 自行推测
如果发生冲突：

*.txt
Plaintext
高优先级覆盖低优先级。
AI 不得自行融合冲突内容。
无法判断时必须停止推断并报告。
例如：

人物旧档案写“右肩受伤”
第十一章正式正文写“左肩中箭”
当前状态快照写“左肩轻伤”
那么写作 AI 应以最新、已批准的状态快照为准，而不是在长文本里随机选择一个。

六、不要把所有信息混成一大段提示词
错误方式：

*.txt
Plaintext
这里是世界观……
这里是人物……
这里是前十章……
这里是文风……
这里是写作技巧……
现在写第十二章……
更合理的是结构化分区：

*.yml
YAML
authority:
  precedence: [...]
task:
  chapter_goal: ...
  start_state: ...
  end_state: ...
mandatory_facts: [...]
forbidden_content: [...]
characters: [...]
locations: [...]
recent_continuity: [...]
relevant_canon: [...]
open_threads: [...]
style: [...]
active_techniques: [...]
output_requirements: [...]
这样 AI 能清楚区分：

哪些是必须服从的
哪些是背景事实
哪些只是参考
哪些是禁止内容
哪些是本章目标
七、长章节最好按场景生成
四五千字以上的章节，如果背景复杂，不建议始终一次生成完成。

推荐工作流：

*.txt
Plaintext
1. 生成章节执行计划
2. 检查章节计划与设定
3. 为每个场景准备独立上下文包
4. 逐场景生成
5. 合并成章
6. 检查场景衔接
7. 检查设定和人物一致性
8. 统一文风
9. 形成候选定稿
场景上下文包
每个场景只需要：

场景目标
开始状态
结束状态
出场人物
地点
本场景相关事实
上一个场景结尾
本场景需要埋设或回收的内容
禁止提前透露的信息
例如：

*.yml
YAML
scene:
  id: chapter_012_scene_02
  goal: 林越进入目标房间
  start_state: 林越已经到达二楼走廊
  end_state: 林越藏在横梁，发现有人进入房间
  characters:
    - 林越
    - 未知搜查者
  required_facts:
    - 林越左肩受伤
    - 房门从内部落锁
  forbidden_reveals:
    - 未知搜查者就是沈青
  previous_scene_tail: 上一场景结尾原文
这样比每个场景都输入整个项目稳定得多。

八、场景生成也不能完全割裂
逐场景生成容易出现另一个问题：

语气断裂
内容重复
人物状态重置
道具位置变化
前后动作接不上
因此每生成一个场景，都要产生一份“场景状态变更”。

*.yml
YAML
scene_result:
  text: 场景正文
  state_changes:
    location:
      lin_yue: 二楼天字三号房横梁
    physical:
      lin_yue: 左肩伤势加重
    knowledge:
      lin_yue:
        added:
          - 有人在他之前搜查房间
    items:
      added:
        - 半枚双尾蛇蜡印
  open_hooks:
    - 房间外出现脚步声
  continuity_tail:
    content: 场景最后若干段
下一场景基于：

*.txt
Plaintext
章节总纲
+ 最新状态
+ 上一场景结尾
+ 下一场景任务
继续生成。

九、上下文需要预算，不是无限添加
可以为每类内容分配预算，而不是谁有资料就全部放进去。

一个概念性比例是：

内容	输入预算建议
任务、目标、约束	10%
章节纲要和场景节拍	15%
人物及故事当前状态	20%
相关世界观和事实	15%
前文衔接	20%
风格样例和写作技巧	10%
冗余与补充空间	10%
这不是固定数字，而是要配置化。

真正的原则是：

先保证目标、当前状态和前文衔接，再考虑增加背景和风格样例。

如果输入超出预算，建议按以下顺序压缩：

删除无关背景；
删除重复事实；
将远距离前文压缩成摘要；
将完整人物档案替换为本章角色卡；
将大量风格范文替换为风格规则卡；
只保留与本章有关的写作技巧；
将次要参考资料改为按需检索。
不能优先压缩的内容是：

本章目标
人物知识边界
强制事实
禁止内容
开始与结束状态
关键伏笔
前一场景衔接
十、让 AI 报告“上下文使用情况”
正文之外，可以要求 AI 返回一份机器可读报告：

*.json
JSON
{
  "status": "completed",
  "draft": "章节正文",
  "context_report": {
    "facts_used": [
      {
        "fact_id": "fact_102",
        "usage": "用于描写巡逻时间"
      }
    ],
    "unused_required_facts": [],
    "possible_conflicts": [],
    "missing_information": [],
    "assumptions": []
  },
  "beat_coverage": [
    {
      "beat_id": "beat_01",
      "covered": true
    }
  ],
  "new_content_candidates": [
    {
      "type": "environment_detail",
      "content": "客栈横梁上积有陈年灰尘",
      "canon_status": "unapproved"
    }
  ]
}
尤其要区分：

既有事实
AI 合理补充的细节
AI 推测
新设定候选
与设定可能冲突的内容
这样 AI 自由发挥出的内容不会自动污染正式设定库。

十一、建议的完整架构
*.txt
Plaintext
项目知识库
├── 正式设定库
├── 人物库
├── 地点库
├── 时间线
├── 事件库
├── 伏笔库
├── 正文版本库
├── 风格规则库
├── 写作技巧库
└── 摘要与索引库
          ↓
章节任务
          ↓
上下文规划器
├── 判断本章需要哪些资料
├── 生成检索请求
└── 制订上下文预算
          ↓
检索器
├── 规则查询
├── 关键词检索
├── 语义检索
└── 关系检索
          ↓
上下文编译器
├── 去重
├── 压缩
├── 版本过滤
├── 优先级排序
├── 冲突检测
└── 格式化
          ↓
章节写作包
          ↓
正文生成器
          ↓
一致性审核
├── 人物审核
├── 时间线审核
├── 设定审核
├── 章节目标审核
└── 风格审核
          ↓
修订器
          ↓
候选定稿
其中最重要的是：

写作 AI 不负责从一大堆混乱资料中自行判断“应该看什么”；上下文系统负责把任务资料整理好，写作 AI 只负责执行。

十二、最简化的结论
写一章时，不应该给 AI：

*.txt
Plaintext
全部世界观
+ 全部人物资料
+ 全部前文
+ 全部写作教程
+ 大量风格范文
而应该给它：

*.txt
Plaintext
本章任务合同
+ 本章相关人物状态
+ 本章相关世界观事实
+ 前文衔接
+ 需要处理的伏笔
+ 精简风格卡
+ 本章启用的写作技巧
+ 明确的禁止项
+ 输出和验收要求
系统可以拥有无限丰富的知识库，但单次调用只使用：

经过检索、压缩、去重、排序和版本校验的最小充分上下文。

因此，后续真正要重点设计的并不只是“写作提示词”，而是三个独立模块：

项目知识与状态管理器
章节上下文规划及编译器
分场景生成与状态接续机制
这三个模块做好以后，背景知识再多，也不会直接变成一团混乱的提示词。
