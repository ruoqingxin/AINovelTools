# R3 检索上下文契约

## 前端展示 UI 固化标准
- 前端展示 UI 在不影响性能的前提下，必须美观、清晰、易用。
- 首次实现功能时确定布局、信息层级、视觉规范、控件规范、完整状态和响应式行为，形成稳定基线。
- 后续功能优先复用既有 UI；除非有明确的可用性、性能或业务依据，不进行大规模改版。
- UI 调整须保持操作路径和数据语义连续，并完成桌面与窄屏检查。

状态：契约已建立，索引和真实检索仍遵守 R4/R6 门槛  
日期：2026-08-27

## 1. 目的

提前固定大模型上下文链的输入输出，不在 R3 提前绑定向量数据库：

```text
用户自然语言要求
    -> 判断当前章节是否已足够
    -> 需要项目知识时执行结构化查询
    -> 可用时补充关键词检索
    -> 语义索引就绪时补充 Embedding 检索
    -> 按来源去重、相关度排序、TokenBudget 截断
    -> 将检索到的原文和固定上下文交给 DeepSeek/OpenAI
```

Embedding 向量只用于计算相似度，不进入聊天 Prompt。聊天模型接收的是检索命中的原文、来源修订和任务上下文。

## 2. 稳定契约

- `KnowledgeChunk`：分块 ID、来源 ID、来源修订、来源哈希、块序号、分块版本、原文。
- `EmbeddingIdentity`：Embedding Profile、模型 ID 和向量维度。模型或维度变化时必须重新生成索引，不能混用。
- `RetrievalEvidence`：知识分块、召回方式和归一化相关度。
- `ContextEvidenceRef`：随上下文包保留的最小证据引用，用于审计和复现。
- `RetrievalPlan`：明确本次使用结构化、关键词或语义检索，以及候选和附加数量上限。

## 3. 调用规则

1. 只处理当前选区、当前章节或章节摘要时，使用 `CURRENT_CHAPTER_ONLY`，不调用 Embedding。
2. 明确需要人物设定、世界观、跨章节事实或项目知识时，使用 `PROJECT_KNOWLEDGE`。
3. 项目知识检索始终优先结构化数据；FTS5 就绪后叠加关键词结果；语义索引就绪后才调用硅基流动 Embedding。
4. 相同分块只保留一次，默认最多召回 24 个候选、向 Prompt 附加 8 个原文分块。
5. 用户要求、选区、章节规划和当前正文属于确定性上下文，不得被 Embedding 结果替代。
6. 没有知识库或没有命中时必须显式标记，不允许模型声称读取过项目设定。

## 4. 当前阶段边界

R3 已实现契约、证据校验、去重排序和可选上下文组装，但默认写作链仍使用 `CURRENT_CHAPTER_ONLY`。R4 建立实体与 FTS5 后可接入结构化和关键词检索；只有稳定来源版本、EvidenceAnchor 和召回评估集具备后，才在 R6 打开语义索引。

该顺序避免为了减少 Prompt 而提前向第二家云服务发送正文，也避免 Embedding 模型切换导致不可追溯的混合向量。
