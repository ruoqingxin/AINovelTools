一、AI 的作用

附加标准：前端展示 UI 固化标准
- 前端展示 UI 在不影响性能的前提下，必须美观、清晰、易用。
- 首次实现功能时确定布局、信息层级、视觉规范、控件规范、完整状态和响应式行为，形成稳定基线。
- 后续功能优先复用既有 UI；除非有明确的可用性、性能或业务依据，不进行大规模改版。
- UI 调整须保持操作路径和数据语义连续，并完成桌面与窄屏检查。
AI 的价值不只是“生成文字”，主要有六类。

1. 理解与提取
把非结构化内容转成结构化信息。

例如：

从小说章节中提取人物、地点、事件
从需求描述中提取功能点
从日志中识别错误原因
从长文档中提炼规则、约束和结论
输入是自然语言，输出可以是 JSON、表格、实体关系或者摘要。

2. 推理与规划
根据目标、现状和约束，给出行动方案。

例如：

规划小说卷纲和章节纲
将开发目标拆成任务
分析角色行为是否符合动机
判断某项修改会影响哪些内容
给出几种方案并比较优缺点
AI 在这里负责的是提出方案和推理依据，而不是自动获得最终决定权。

3. 内容生成
根据已批准的规划产生具体内容。

例如：

小说正文
人物小传
场景描写
代码骨架
测试用例
设计文档
生成不应是“自由发挥”，而应该是：

在给定事实、目标、风格、边界和验收标准下完成内容。

4. 检查与评审
AI 可以扮演独立审核者。

例如：

连贯性检查
设定冲突检查
时间线检查
角色行为一致性检查
代码审查
需求覆盖检查
输出格式检查
这里要特别注意：

生成者和审核者最好是两个独立调用，甚至使用不同提示词、上下文和模型。

不能让 AI 写完后只问一句“你写得对不对”，因为它容易为自己的结果辩护。

5. 修改与修复
根据明确的问题单执行局部修改。

例如：

修复人物称谓错误
调整某段节奏
补足伏笔
修复函数实现
统一文档格式
修复任务应尽量给 AI：

原始内容
问题位置
问题类型
修改边界
不允许改变的部分
修改后的验收条件
6. 协调与解释
AI 可以帮助人和系统理解当前状态。

例如：

解释为什么产生冲突
汇总多个审核器的意见
比较多个候选方案
生成变更说明
将技术结果转成用户容易理解的表达
但“协调”不等于“最终裁决”。涉及高影响决策时，最好保留人工确认或确定性规则。

二、AI 的定位
我建议把 AI 定位成：

有专业角色、有任务边界、有输入合同、有输出合同、无默认最终裁决权的认知服务。

这里有几个概念必须分开。

概念	回答的问题
角色	AI 以什么身份思考
任务	AI 这一次具体要做什么
能力	AI 能分析、生成或检查什么
权限	AI 可以读取和修改什么
责任	AI 必须对哪些结果负责
禁区	AI 绝对不能做什么
验收	如何判断这次结果合格
例如：

*.txt
Plaintext
角色：小说连续性审核员
任务：检查第12章与既有设定是否冲突
能力：分析人物、时间线、空间关系和世界观规则
权限：读取人物卡、时间线、第1—12章；不能修改正文
责任：列出冲突位置、依据、严重程度和修复建议
禁区：不能新增未经确认的设定
验收：每个问题都必须提供原文位置和设定依据
这比简单地说“帮我检查一下第十二章”稳定得多。

三、AI 不应该被定位成什么
1. 不是事实数据库
AI 参数中的知识不能天然视为项目事实。

项目事实必须来自：

当前输入
项目数据库
已批准设定
检索出来的文档
工具返回结果
确认过的历史记录
应该区分：

*.txt
Plaintext
模型知识 ≠ 项目事实
AI 推测 ≠ 已确认设定
生成内容 ≠ 已生效内容
2. 不是最终裁决者
AI 可以：

提出意见
给出评分
推荐方案
解释依据
但不应默认有权：

删除正式内容
修改核心设定
覆盖用户决定
将草稿直接发布
将推测写入事实库
自动解决重大冲突
最终裁决可以属于：

用户；
明确的业务规则；
审核流程；
获得特定授权的 Agent。
3. 不是无限上下文容器
不能把整个项目不加选择地全部塞给 AI。

这样会产生：

重点被淹没
成本上升
推理质量下降
不同版本相互污染
过期信息影响判断
无法追踪结论来自哪里
更合理的是：

根据任务，检索并组装“最小充分上下文”。

也就是：内容尽量少，但足够完成任务。

4. 不是可靠的确定性程序
适合用普通代码做的事情，不应全部交给 AI。

例如：

字段格式校验
ID 唯一性检查
时间计算
权限判断
数据库事务
版本覆盖规则
状态机流转
文件是否存在
可采用这样的分工：

*.txt
Plaintext
普通程序：确定性规则
AI：语义理解、模糊判断、生成和复杂推理
人工：价值判断、重大决策、最终确认
四、每次调用应该给 AI 什么
可以建立统一的 AI 输入合同。

1. 角色
告诉 AI 以什么专业身份工作。

*.txt
Plaintext
你是人物一致性审核员。
角色不要写得过于宽泛。
“你是一名强大的专家”基本没有约束力。

2. 任务目标
说明这次必须完成什么。

不够明确：

*.txt
Plaintext
分析这一章。
更明确：

*.txt
Plaintext
检查本章人物行为是否与已批准的人物动机、关系和当前状态一致。
最好一次调用只设置一个主要目标，最多带少量次要目标。

3. 当前对象
明确 AI 正在处理什么：

哪个项目
哪个文件
哪一章
哪个版本
哪段文本
哪个任务 ID
例如：

*.json
JSON
{
  "project_id": "novel_001",
  "chapter_id": "chapter_012",
  "version": 4,
  "task_id": "review_20260826_003"
}
这对于后续追踪、重试和回滚非常重要。

4. 事实和上下文
上下文最好分层，不要混成一段。

第一层：强制事实
已经确认，AI 不得改写。

例如：

人物年龄
已发生事件
世界观规则
当前时间
已批准决策
第二层：任务相关材料
本次分析直接需要的内容：

当前章节
相关人物卡
前序事件
当前章节纲要
第三层：参考信息
可用于辅助，但不具有强制性：

风格样例
候选构思
未批准草案
历史建议
第四层：禁止使用或过期信息
明确告诉 AI：

哪些版本已废弃
哪些内容只是设想
哪些结论已经被否决
这是防止上下文污染的重要机制。

5. 约束
约束至少可以分成五类。

内容约束
*.txt
Plaintext
不能新增人物。
不能改变既定事件结果。
不能泄露下一卷秘密。
范围约束
*.txt
Plaintext
只修改第3—7段。
不调整其他段落。
风格约束
*.txt
Plaintext
使用第三人称限知视角。
保持克制、冷峻的叙述风格。
避免网络化表达。
结构约束
*.txt
Plaintext
必须输出合法JSON。
所有问题必须包含位置、依据和建议。
权限约束
*.txt
Plaintext
只允许提出修改建议，不允许直接生成替换正文。
6. 可用工具和数据来源
需要告诉 AI：

能调用哪些工具
每个工具做什么
什么情况下调用
什么情况下不能调用
工具结果和模型推测谁优先
例如：

*.txt
Plaintext
人物事实必须通过人物库查询。
章节原文必须从当前版本读取。
如果数据库记录与模型记忆冲突，以数据库为准。
7. 验收标准
这是最容易被忽略，但最重要的部分。

例如：

*.txt
Plaintext
合格条件：
1. 找出所有明显设定冲突；
2. 每个问题标注原文位置；
3. 每个判断必须引用对应设定；
4. 区分确定冲突和潜在风险；
5. 不得把推测描述成事实；
6. 无问题时明确输出“未发现冲突”。
没有验收标准，AI 只能自己猜测什么叫“做好了”。

8. 不确定性处理方式
必须告诉 AI：不知道时怎么办。

建议要求：

*.txt
Plaintext
如果依据不足：
- 不得自行补充事实；
- 标记为 insufficient_context；
- 说明缺少什么信息；
- 给出需要查询的数据项。
比“不要胡编”更可执行。

9. 输出格式
输出格式应该在调用之前确定，不能让 AI 自由决定。

如果结果需要进入程序，优先使用结构化输出。

例如：

*.json
JSON
{
  "task_id": "review_20260826_003",
  "status": "completed",
  "summary": "",
  "issues": [],
  "uncertainties": [],
  "recommended_actions": []
}
五、要求 AI 输出什么
AI 输出不应只有一段“看起来不错”的文字，而应包括几个层次。

1. 任务结论
直接回答有没有完成任务、整体结果如何。

*.json
JSON
{
  "result": "found_issues",
  "issue_count": 3
}
2. 结果内容
这是任务本身的主体。

例如审核结果：

*.json
JSON
{
  "issues": [
    {
      "type": "character_motivation_conflict",
      "severity": "high",
      "location": {
        "paragraph": 12,
        "quote": "……"
      },
      "description": "角色主动透露秘密，与其当前防备状态冲突。",
      "evidence": [
        {
          "source_id": "character_chen_01",
          "field": "current_goal",
          "content": "隐藏调查结果"
        }
      ],
      "suggestion": "改为试探性表达，或增加被迫透露的触发事件。"
    }
  ]
}
3. 依据
AI 的判断最好可追溯到具体来源。

依据至少应包含：

来源 ID
来源版本
所在位置
使用了哪条规则
依据内容摘要
不要只要求“说明原因”，而要要求“指出依据来自哪里”。

4. 不确定项
AI 应主动汇报哪些地方无法确认。

*.json
JSON
{
  "uncertainties": [
    {
      "question": "角色是否已经得知王城失守？",
      "reason": "当前上下文没有发现对应事件记录。",
      "required_data": [
        "第8—10章事件摘要",
        "角色知识状态记录"
      ]
    }
  ]
}
5. 建议动作
输出不只是问题，还应说明下一步怎么处理。

但建议要和实际执行分开：

*.json
JSON
{
  "recommended_actions": [
    {
      "action": "revise_paragraph",
      "target": "paragraph_12",
      "priority": "high",
      "requires_confirmation": true
    }
  ]
}
这里的 requires_confirmation 很重要。

6. 变更记录
如果 AI 被授权修改内容，应返回：

修改了什么
为什么修改
修改前是什么
修改后是什么
是否影响其他内容
是否需要重新审核
例如：

*.json
JSON
{
  "changes": [
    {
      "target_id": "paragraph_12",
      "operation": "replace",
      "before": "原始内容",
      "after": "修改内容",
      "reason": "修复人物动机冲突",
      "side_effects": [
        "需要复查第15段对话衔接"
      ]
    }
  ]
}
7. 自检结果
可以要求 AI 按验收标准进行形式化自检：

*.json
JSON
{
  "self_check": {
    "output_schema_valid": true,
    "all_issues_have_evidence": true,
    "unsupported_facts_detected": false,
    "scope_violations": []
  }
}
不过要注意：

AI 自检只能作为第一道检查，不能替代程序校验或独立审核。

六、输入和输出的核心关系
可以把一次 AI 调用抽象为：

*.txt
Plaintext
AI任务 =
角色
+ 目标
+ 当前对象
+ 事实上下文
+ 约束
+ 权限
+ 可用工具
+ 输出格式
+ 验收标准
输出则是：

*.txt
Plaintext
AI结果 =
任务状态
+ 主要结论
+ 结构化结果
+ 判断依据
+ 不确定项
+ 建议动作
+ 变更记录
+ 自检信息
也可以形成一个完整合同：

*.txt
Plaintext
给 AI：
“你是谁、要做什么、基于什么、能做什么、不能做什么、
遇到未知怎么办、什么叫完成。”
要求 AI 输出：
“做出了什么结论、依据是什么、哪里不确定、建议怎么处理、
是否修改了内容、修改影响了什么。”
七、建议的 AI 角色分层
对于比较复杂的系统，尤其是 AI 辅助小说创作系统，我建议不要只设置一个“写作 AI”，而是分成不同职责。

第一层：顾问型 AI
负责：

分析
解释
提供候选方案
风险提示
特点：

只读
不修改正式数据
输出建议
第二层：规划型 AI
负责：

任务拆分
情节规划
章节规划
修改计划
检索计划
特点：

生成计划
计划需要批准
不直接改正式内容
第三层：执行型 AI
负责：

写正文
改正文
生成代码
填充结构化数据
特点：

只能在授权范围内操作
必须返回变更记录
输出先进入草稿区
第四层：审核型 AI
负责：

检查执行结果
查找冲突和遗漏
判断是否满足验收标准
特点：

不参与原始生成
不直接掩盖问题
审核结果可被追溯
第五层：协调型 AI
负责：

汇总多个 AI 的结果
消除重复意见
识别审核意见冲突
生成待用户决策清单
特点：

可以组织意见
不应偷偷替用户决策
第六层：治理与裁决层
这一层不应完全等同于普通 AI。

负责：

权限控制
状态流转
冲突仲裁
正式版本确认
快照与回滚
操作审计
应该以程序规则和人工确认为主，AI 只提供辅助意见。

八、建议采用“双输出”
AI 每次既输出给人看，也输出给程序用。

人类可读输出
例如：

*.txt
Plaintext
本章发现2个高风险问题：
1. 主角提前知道了尚未发生的事件；
2. 配角行为与其当前利益目标不符。
建议先修复第一个问题，因为它会影响后续三个场景。
机器可读输出
*.json
JSON
{
  "status": "found_issues",
  "counts": {
    "high": 2,
    "medium": 1,
    "low": 0
  },
  "issues": []
}
双输出的好处是：

人能快速理解
程序能继续处理
能进入工作流
能建立统计、审计和自动测试

十、在小说创作系统里的具体例子
假设任务是：生成第十二章正文。

给 AI 的内容
*.txt
Plaintext
角色：
你是正文执行器，不负责修改世界观和章节目标。
目标：
根据已批准的第十二章章节纲生成正文。
强制事实：
- 当前日期为大陆历317年冬月初三；
- 林越不知道沈青的真实身份；
- 城门已经封闭；
- 本章结尾必须是密信被发现。
任务材料：
- 第十二章章节纲；
- 人物当前状态；
- 第十一章结尾；
- 本章相关地点设定；
- 必要的语言风格样例。
约束：
- 3500—4500字；
- 第三人称限知视角；
- 不新增命名人物；
- 不解释反派真实计划；
- 不修改既有事件；
- 不超出本章时间范围。
权限：
- 只能生成候选草稿；
- 不得写入正式章节；
- 发现纲要冲突时停止推断并报告。
验收：
- 完成所有章节节拍；
- 人物知识边界正确；
- 结尾落在密信被发现；
- 不出现设定外信息。
要求 AI 输出
*.json
JSON
{
  "status": "completed",
  "draft": "正文内容",
  "beat_coverage": [
    {
      "beat_id": "beat_01",
      "covered": true,
      "location": "第1—4段"
    }
  ],
  "facts_used": [],
  "new_content_candidates": [],
  "uncertainties": [],
  "possible_conflicts": [],
  "self_check": {
    "word_count_valid": true,
    "viewpoint_valid": true,
    "ending_requirement_met": true
  }
}
其中 new_content_candidates 用来承接 AI 生成但尚未批准的新细节，例如：

*.json
JSON
{
  "new_content_candidates": [
    {
      "type": "location_detail",
      "content": "城门内侧悬挂三盏铜灯",
      "status": "unapproved",
      "should_persist": false
    }
  ]
}
这样就不会把 AI 随手写出的细节直接当成永久世界观设定。

十一、最重要的设计原则
最后可以归纳成十条：

AI 必须有明确角色，不能只是“万能助手”。
角色、任务、能力和权限必须分开定义。
项目事实必须来自可靠数据源，而不是模型记忆。
每次调用只提供最小充分上下文。
已批准事实、参考内容和废弃信息必须分层。
输入必须包含目标、约束和验收标准。
输出必须结构化、可追踪、可验证。
事实、推测、建议和生成内容必须明确区分。
重大修改必须经过审核、确认、快照和回滚机制。
AI 负责认知工作，程序负责确定性规则，人负责最终价值判断。
最简洁地说：

给 AI 的不是一堆资料，而是一份完整的任务合同；要求 AI 输出的不是一段答案，而是一份可验证、可追踪、可进入下一步工作流的任务结果。
