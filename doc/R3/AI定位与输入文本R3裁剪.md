# AI 定位与输入文本的 R3 裁剪

## 前端展示 UI 固化标准
- 前端展示 UI 在不影响性能的前提下，必须美观、清晰、易用。
- 首次实现功能时确定布局、信息层级、视觉规范、控件规范、完整状态和响应式行为，形成稳定基线。
- 后续功能优先复用既有 UI；除非有明确的可用性、性能或业务依据，不进行大规模改版。
- UI 调整须保持操作路径和数据语义连续，并完成桌面与窄屏检查。

## 1. 裁剪原则

R3 只实现能够在当前“云端调用 -> Proposal -> 人工审核 -> 编辑草稿”闭环中独立验证的规则。依赖正式知识实体、状态投影、结构化输出治理、多个模型角色或持久化工作流的能力，不做空壳 UI，分别进入 R4-R6。

## 2. R3 立即实现

### AI 定位

- AI 是有专业角色、任务边界、输入合同和输出合同的认知服务。
- AI 不是项目事实数据库，不得把模型记忆或推测当成项目事实。
- AI 没有默认最终裁决权，只能生成 `AiProposal`；接受后也只修改编辑草稿。
- 程序负责选区校验、权限、状态流转、版本、事务和审计等确定性规则。

### 每次调用的任务合同

- `role`：续写使用候选正文执行器，重写和润色使用选区修订执行器，摘要使用章节摘要执行器。
- `goal`：每次调用只有一个主要目标。
- `target`：记录章节 ID、目标正文修订和处理对象类型。
- `permissions`：只读取本次上下文并生成一个待审核候选。
- `forbidden_actions`：不得修改正式正文、不得固化推测、不得越过目标范围。
- `acceptance_criteria`：按动作固定最低验收条件。
- `uncertainty_policy`：关键依据不足或冲突时报告上下文不足，不得自行补事实。
- `output_contract`：R3 保持纯文本候选，以兼容流式预览和 Proposal 审核。

### 上下文权威层级

```text
P0 用户本次明确指令、任务范围和输出合同
P1 已批准事实
P2 已批准章节规划
P3 故事当前状态
P4 当前编辑草稿和前文衔接
P5 风格规范
P6 参考信息
P7 模型推测，仅允许作为未批准候选，不得作为输入事实
```

高优先级覆盖低优先级；发现冲突时不得自行融合。当前 R4/R5 数据尚未建立的层必须明确显示无来源，不能伪装成已读取项目知识。

### 上下文编译和审计

- ContextAssembler 按优先级组织分区，不把所有资料混成一段。
- TokenBudget 先保留任务合同、用户指令和高权威材料。
- 续写正文被截断时保留靠近结尾的内容，以维持衔接。
- 每个上下文包记录分区类型、优先级、来源数量、实际字符数和截断状态。
- `ai_tasks` 持久化任务合同和分区审计元数据，但不复制完整 Prompt、正文或检索原文。
- 检索证据额外标记 `AUTHORITATIVE_FACT`、`TASK_MATERIAL` 或 `REFERENCE`，避免不同权威资料混用。

## 3. 延后到 R4

- Character、Location、Faction、Item、Concept 等长期知识库。
- SQLite FTS5 关键词检索、来源版本过滤和本章相关资料查询。
- 章节 L0-L5、人物 L0-L3 等多精度摘要与压缩材料的基础数据。
- 风格规则卡、少量样例和写作技巧卡的正式管理入口。

R4 建立数据和检索来源，但不让检索结果自动成为正式事实。

## 4. 延后到 R5

- 故事当前状态、人物知识边界、物品和位置等 `WorldState` 投影。
- `EvidenceAnchor`、事实依据、冲突和不确定项的正式追溯。
- 人类可读结果加机器可读 JSON 的双输出及 Schema 校验。
- `facts_used`、`possible_conflicts`、`new_content_candidates`、变更记录和自检报告。
- 独立生成与独立审核调用，以及候选知识的人工批准流程。

这些输出会进入知识治理，必须等正式领域类型和审核事务具备后再启用。

## 5. 延后到 R6

- 使用专门 AI 制订检索计划或上下文计划。
- 关系检索、向量索引、混合检索和高级 ContextAssembler。
- 长章节按场景规划、逐场景生成、状态接续、合章和多轮审核。
- 顾问、规划、执行、审核和协调等多角色工作流。
- 多模型审核、可恢复任务 Runtime 和独立 Worker。

这些能力需要评估集、性能基准和持久化工作流，不在 R3 增加空入口。

## 6. R3 验收

1. 四个动作均生成明确且可序列化的任务合同。
2. Prompt 明确 AI 无事实裁决权和正式写入权。
3. 上下文采用 `P0-P6` 分区，缺失来源会显式报告。
4. TokenBudget 截断可以审计，续写优先保留正文尾部。
5. Prompt 和上下文版本随合同内容变化，任务可追溯。
6. 不改变当前四页签 UI 和 Proposal 审核路径。
