## 1. 目标

将 R5 已完成的可追溯知识、EvidenceAnchor、ChangeSet 和项目可靠性能力，转化为高级能力可以安全接入的准入机制。R6 的价值不是堆叠架构，而是只在真实需求和可验证证据出现时，选择一个高级能力完成端到端交付。

## 2. 当前批准范围

### 阶段 A：能力准入与评测基线（暂停）

- [x] 完成 R0-R2、R3、R5 和长期按需延期项的复核。
- [x] 为候选能力定义触发证据、隐私边界、失败路径和验收门禁。
- [ ] 完成 R5 全量体验巡检并归档已发现问题。
- [ ] 建立首个脱敏评测数据集及其版本、来源和预期结果。
- [ ] 选择首个满足门槛的高级能力并建立 ADR。

### 阶段 B：按需实现切片

只有获得批准的一个能力可以进入本阶段。候选项包括：

| 候选能力 | 当前状态 | 批准条件 |
|---|---|---|
| 向量/混合检索 | 未批准 | 评测集、召回指标、隐私确认、重建策略 |
| Tantivy | 未批准 | FTS5 基准未达标或需要其评分/分词能力 |
| ReviewCase 批量审核 | 未批准 | 单章节 ChangeSet 出现批量队列或多来源治理缺口 |
| 长章节场景工作流 | 未批准 | 至少一个稳定重复的长章节工作流与验收样例 |
| 完整 Task Runtime / Worker | 未批准 | 多个长任务需要恢复、Lease、Checkpoint 或进程隔离 |
| 图谱、时间线或节奏分析 | 未批准 | 明确创作决策场景和可验证输出 |

## 3. 每个获批能力的必经步骤

1. 新增 ADR，记录触发数据、替代方案和不实施理由。
2. 定义领域输入、输出、权限与错误；不得绕过 R5 的知识审核和证据边界。
3. 若需持久化，先登记迁移、索引和回滚策略。
4. 定义隐私边界；模型、Embedding 与检索发送内容必须可审计。
5. 实现加载、空、成功、冲突、失败、取消和恢复状态。
6. 完成领域、SQLite、桌面交互、性能或召回评测，并更新 FeatureCatalog 和验收记录。

## 4. 阶段出口

- 至少一个高级能力满足门槛并完成独立 ADR、实现、评测和验收；或
- 明确记录所有候选项仍未满足门槛，R6 保持在准入基线阶段，不以空实现冒充完成。

## 5. 明确不在本阶段默认实现

账号、云端托管、多人协作、计费、任意代码插件和公网遥测仍不在当前产品范围。其余高级能力未满足门槛时继续延期，不得因为 R6 已开始而提前建立空壳。
