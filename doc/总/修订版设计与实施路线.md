# AI 辅助长篇小说创作系统：修订版设计与实施路线

## 前端展示 UI 固化标准
- 前端展示 UI 在不影响性能的前提下，必须美观、清晰、易用。
- 首次实现功能时确定布局、信息层级、视觉规范、控件规范、完整状态和响应式行为，形成稳定基线。
- 后续功能优先复用既有 UI；除非有明确的可用性、性能或业务依据，不进行大规模改版。
- UI 调整须保持操作路径和数据语义连续，并完成桌面与窄屏检查。

## 2. 修订结论

原设计的业务方向正确，主要问题是工程骨架过重。首版同时建设大量 Registry、通用 Bus、Disabled Adapter、独立 Blob 生命周期、外部全文索引和完整任务运行时，会延迟第一个可用版本，并增加尚无真实调用者的维护成本。

本次修订采用以下总原则：

```text
关键业务不变量保持完整
+ 真实纵向切片优先
+ 成熟的本地组件优先
+ 静态、显式代码优先
+ 复杂能力按触发条件引入
```

修订后的直接好处：

1. 更早形成可运行产品：R0 即打通创建和打开项目，而不是只展示占位页面。
2. 更少自研框架：不提前开发九类注册表、通用消息总线和插件式分发系统。
3. 更简单的数据一致性：正文、修订和元数据首版统一进入 SQLite。
4. 更容易备份恢复：首版的核心备份对象主要是一个项目数据库和清晰的附件目录。
5. 更低的调试成本：Command、Query 和 Handler 使用显式调用链，容易定位错误。
6. 更少重复契约：Rust 类型是内部 IPC 的主要真源，生成 TypeScript 类型。
7. 更平滑的演进：Tantivy、向量索引、独立 Worker 和工作流引擎都有明确引入条件。
8. 不牺牲可靠性：不可变修订、AI Proposal、人工审核、原子定稿和 Secret Store 继续保留。

## 3. 不得简化的核心规则

以下规则属于产品正确性，不以减少代码为理由取消：

```text
规划 != 实际正文
编辑草稿 != 正式正文修订
AI 输出 != 已接受正文
AI 推断 != 正式故事知识
角色认知 != 世界事实
恢复记录 != ManuscriptRevision
搜索索引 != 正式数据源
普通保存 != 章节定稿
```

同时必须保证：

- 正文修订不可覆盖，只能创建新修订。
- AI 输出先保存为 `AiProposal`，由用户接受、部分接受或拒绝。
- API Key 不进入项目数据库、日志、诊断包或前端可回读状态。
- 已定稿章节只能通过替代定稿更新，旧定稿永久保留。
- 正式知识变更和定稿记录在一个 SQLite 事务内提交。
- 搜索、向量、可视化和 AI 分析失败，不得破坏正式正文。
- 备份必须经过恢复演练和哈希验证，不能只验证压缩包生成成功。

## 4. 修订后的技术基线

### 4.1 桌面和前端

- Tauri 2
- React + TypeScript + Vite
- pnpm Workspace
- Tiptap / ProseMirror
- TanStack Router
- TanStack Query
- React Hook Form + Zod，仅用于表单和不可信输入
- Radix Primitives
- Tailwind CSS
- Lucide React

以下依赖按实际页面引入，不在 R0 预装或预建封装：

- Zustand：出现跨路由工作区状态时引入。
- TanStack Virtual：列表达到需要虚拟化的规模时引入。
- TanStack Table：出现复杂表格时引入。
- dnd-kit：规划树需要拖拽时引入。
- React Flow、Sigma.js、ECharts：对应高级功能阶段再引入。

### 4.2 Rust 和数据库

- Rust stable，使用 `rust-toolchain.toml` 固定版本。
- `rusqlite` 作为首版 SQLite 访问层，启用 bundled SQLite，确保开发和运行环境一致。
- 使用成熟的编号 SQL Migration 方案；具体 crate 在 R0 通过最小验证后锁定。
- SQLite 启用 WAL、foreign keys、busy timeout，并在 R0 用集成测试固定 PRAGMA。
- 使用短事务和 `expected_version` 乐观并发。
- 写操作通过应用服务串行协调，不在多个模块中各自持有隐式写连接。

选择 `rusqlite` 的原因：本产品是单用户、本地、SQLite 单写者场景，同步事务模型更直接，也不需要维护 SQLx 离线查询元数据。若 R0 验证发现现有 Tauri 运行模型无法满足后台任务要求，可通过 ADR 改回 SQLx。

### 4.3 类型和契约

- Rust `serde` 类型是内部 Tauri IPC 契约真源。
- 使用经过 R0 验证的类型生成工具生成 TypeScript 类型和客户端薄封装。
- Zod Schema 只用于表单、导入文件、AI 结构化输出和其他不可信边界。
- 不要求每个内部 DTO 同时维护 Rust、TypeScript 和 JSON Schema 三份定义。
- 领域 ID 使用强类型包装，不在领域层传播裸字符串。

### 4.4 测试工具

- Rust：内置测试 + 临时 SQLite 集成测试。
- 前端：Vitest + Testing Library。
- 浏览器态关键流程：Playwright。
- Tauri 桌面 E2E：只保留启动、IPC、文件选择和 Secret Store 等少量桌面专属冒烟测试。
- 备份、恢复、迁移和崩溃恢复必须使用真实临时目录和真实 SQLite。

## 5. 简化后的总体架构

首版采用显式分层的模块化单体，但不实现通用框架式 Bus：

```text
React UI
  -> typed Tauri client
  -> Tauri command/query facade
  -> Application Service / Handler
  -> Domain model and rules
  -> Repository / Provider Port
  -> SQLite, filesystem, model API, OS Secret Store
```

依赖规则：

- Domain 不依赖 Tauri、SQLite、HTTP 和 UI。
- Application 依赖 Domain，并定义需要的 Port。
- Infrastructure 实现 Repository 和 Provider Port。
- Tauri facade 只负责验证、调用、错误映射和 DTO 转换。
- UI 不直接访问 SQLite、模型 Provider 或项目内部文件。
- AI、搜索和后台任务只能产生 Proposal、投影或候选结果。

### 5.1 首批物理结构

```text
AINovelTools/
├─ apps/
│  └─ desktop/
│     ├─ src/
│     └─ src-tauri/
├─ crates/
│  ├─ novel-domain/
│  ├─ novel-application/
│  └─ novel-infrastructure/
├─ packages/
│  └─ ui/
├─ tests/
├─ docs/
└─ tools/
```

说明：

- API facade 位于 `apps/desktop/src-tauri`，首版不单独建立 `novel-api` crate。
- IPC DTO 首版放在 application 或 desktop 的明确模块中，不单独建立 `novel-contracts` crate。
- 测试辅助代码先放各 crate 的 `tests/common`，有两个以上消费者后再拆 `novel-test-support`。
- AI、搜索、工作流和可观测性先作为 infrastructure/application 内部模块，有明确编译边界或 Worker 复用需求后再拆 crate。

## 6. Command、Query、Event 和 Feature

### 6.1 Command 和 Query

Command 和 Query 保留语义，但首版采用显式 Handler：

```text
CreatePlanNode command
  -> create_plan_node handler
  -> domain validation
  -> repository transaction
  -> typed result
```

不在 R0 建设动态 `CommandRegistry`、`QueryRegistry` 和反射式 Handler 查找。命令版本只在需要跨版本持久化、导入或长期任务重放时增加。

### 6.2 Event 和 Outbox

只有满足以下任一条件才创建 Domain Event：

- 另一个领域需要响应。
- 事务外必须执行索引、备份或后台任务。
- 需要可靠 Outbox。
- 该事件是审计或定稿历史的一部分。

普通的同模块 UI 更新不需要事件，通过 Query 精确失效完成。

### 6.3 Feature 状态

首版只建立一个静态 `FeatureCatalog`：

```text
feature_id
display_name
stage
status
required_capabilities
unavailable_reason
```

状态继续使用：

```text
DECLARED
PARTIAL
IMPLEMENTED
DISABLED
EXPERIMENTAL
```

未实现页面返回 `FEATURE_NOT_AVAILABLE`。只有已经存在调用者的 Port 才需要 Disabled Adapter；不再为所有未来能力提前创建空接口和 Stub。

## 7. 数据与文件存储修订

### 7.1 项目目录

```text
NovelProject/
├─ project.json
├─ project.sqlite
├─ attachments/
├─ snapshots/
├─ recovery/
├─ exports/
└─ temp/
```

调整说明：

- 应用日志默认放操作系统应用数据目录，不进入小说项目和普通备份。
- 全文搜索首版使用 SQLite FTS5，因此不需要 `indexes/fulltext`。
- `blobs` 不再承担正文修订存储，改为按真实需要使用 `attachments` 或后期 Blob Store。
- 最近项目列表属于应用级数据，不写入小说项目数据库。

### 7.2 正文修订

R0-R5 阶段，正文修订的 Tiptap JSON 直接保存在 SQLite：

```text
manuscript_revisions
├─ id
├─ project_id
├─ chapter_id
├─ parent_revision_id
├─ base_revision_id
├─ document_schema_version
├─ document_json
├─ content_hash
├─ created_at
└─ creation_reason
```

每个正文块继续使用稳定 `block_id`。保存新修订只允许 INSERT，数据库权限和 Repository 测试禁止 UPDATE/DELETE 历史修订内容。

附件、完整模型原始响应和大型快照可以进入文件存储，并使用内容哈希、临时文件、原子重命名和引用记录。正文是否迁移到独立 Blob Store，必须由真实数据库规模和性能测试触发。

### 7.3 备份恢复

首版备份流程：

```text
刷新编辑恢复状态
-> 建立 SQLite 一致性副本
-> 收集被数据库引用的附件
-> 写入 manifest 和哈希
-> 生成备份包
-> 恢复到新目录验证
```

默认禁止覆盖当前项目。恢复验收必须比较项目 ID、Schema 版本、章节数量、当前修订 ID 和正文内容哈希。

## 8. 搜索修订

R4 首先采用 SQLite FTS5 trigram：

```text
chapters / manuscript revisions / plan nodes / entities
  -> FTS5 projection
  -> search query
  -> object_id + block_id + snippet
```

要求：

- FTS 表是投影，可从正式表重建。
- 正式写入和小型 FTS 更新尽量同事务完成。
- 一到两个汉字的短查询可使用受限 `LIKE` 回退。
- 搜索结果必须定位到项目对象和正文块。

满足以下任一条件后，才评估引入 Tantivy：

- FTS5 在 LARGE 数据集上达不到已经定义的性能目标。
- 需要成熟的中文词典分词、字段权重和复杂评分。
- 索引更新明显拖慢正式保存事务。
- 需要与向量结果进行统一的高级融合。

引入 Tantivy 时，通过 Outbox 异步构建；SQLite 继续是唯一正式数据源。

## 9. AI 接入修订

### 9.1 Provider

R3 按模型能力拆分云端 Adapter：

- `CHAT`：DeepSeek、OpenAI API 和用户配置的 OpenAI-compatible 云端接口。
- `EMBEDDING`：硅基流动 Embeddings API。
- Chat Adapter 支持流式文本、取消、超时、有限重试和错误归一化。
- Embedding Adapter 只负责文本向量化和维度校验；向量索引、召回和混合检索仍按 R6 门槛实施。

当前产品不提供 Ollama 或其他本地模型部署入口。OpenAI Responses 专用 Adapter 在确有专属能力需求时通过 ADR 引入，不在首版同时维护多套文本生成协议。

### 9.2 AI 请求链

```text
用户选择功能
-> ContextAssembler 收集有来源的上下文
-> PrivacyPolicy 检查外发内容
-> TokenBudget 保守估算
-> ModelGateway 调用
-> 流式预览
-> 保存 AiProposal
-> 用户接受、部分接受或拒绝
-> 编辑器产生新草稿
-> 用户保存新 ManuscriptRevision
```

首批功能保持为：续写、重写选区、润色选区和章节摘要。

R3 不实现通用 Agent、ToolGateway、函数调用工作流和多 Agent 调度。Prompt 使用版本化模板文件和内容哈希，不提前建设 Prompt CMS。

## 10. 后台任务修订

R4 建立简单、持久化的本地 Job Runner：

```text
jobs
├─ id
├─ job_type
├─ payload
├─ status
├─ progress
├─ attempt_count
├─ cancel_requested
├─ error_summary
├─ created_at
└─ updated_at
```

支持 `QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED`、取消、有限重试和启动恢复。第一批只承载备份、恢复验证、健康扫描和 FTS 重建。

Lease、Checkpoint、ResourceGovernor、独立 Worker、补偿和复杂优先级推迟到 R6。普通短任务直接在应用服务中执行，不强制进入任务队列。

## 11. 知识审核和定稿修订

单用户首版将审核状态收敛到：

```text
ChapterChangeSet
  -> ChangeItem[]
     - kind
     - payload
     - evidence
     - risk
     - conflict
     - decision
     - modified_payload
```

R5 不单独建立通用审核队列框架。只有出现跨章节批量审核、多个审核来源或真正的任务分派需求后，才拆出 `ReviewCase` 和 `ReviewItem`。

正式知识仍使用明确的 Entity、Relation、Fact、Event、Belief 和 Foreshadowing 模型，不能把它们永久塞入无约束 JSON。候选阶段可以使用带版本 Schema 的 `ChangeItem.payload`，批准提交时必须转换并验证为正式领域类型。

定稿事务包含：

```text
FinalizationRecord
+ 章节状态和目标 ManuscriptRevision
+ 已批准的正式知识变化
+ KnowledgeVersion
+ AuditRecord
+ Outbox
```

大型索引更新、影响分析和快照压缩在事务外执行。

## 12. 修订后的实施阶段

### R0：可运行基础和项目纵向切片

交付：

- Cargo、pnpm 和 Tauri Workspace。
- React AppShell、路由、错误边界和基础主题。
- 三个首批核心 crate。
- 强类型 ID、统一错误和时间类型。
- SQLite 连接、Migration、PRAGMA 和健康检查。
- 静态 FeatureCatalog。
- `CreateProject`、`OpenProject`、`CloseProject`。
- 项目临时目录创建和原子完成。
- Rust/TypeScript 类型生成验证。
- 单元、数据库集成和桌面启动冒烟测试。

验收：应用可启动，能够创建、关闭并重新打开项目；创建失败不留下有效半成品；Health Query 显示真实状态。

### R1：项目与规划

交付：

- ProjectSettings 和最近项目。
- PlanNode、PlanRevision 和规划树。
- `WORK_DESIGN/OUTLINE/VOLUME/CHAPTER/SCENE`。
- 新建、编辑、移动、归档和恢复。
- 乐观并发和不可变规划修订。
- 虚拟化规划树在数据规模达到阈值时启用。

验收：可以完成作品设计、总纲、分卷、章节和场景规划；规划不会冒充实际章节。

### R2：正文、恢复和不可变修订

交付：

- Chapter、Scene、NovelDocument v1 和稳定 block ID。
- Tiptap 编辑器。
- 前端短期恢复和 Rust 持久化 RecoveryLog。
- ManuscriptRevision 只追加存储。
- 修订历史、恢复为新草稿和基础三方合并。
- 内容哈希和故障注入测试。

验收：模拟异常退出后正文可恢复；正式保存总是创建新修订；冲突不会静默覆盖。

### R3：AI 创作闭环

交付：

- ModelProfile、OS Secret Store 和 ModelGateway。
- DeepSeek、OpenAI API 和通用 OpenAI-compatible 云端文本接入。
- 硅基流动 Embedding Adapter；不提前建设向量索引和检索。
- ContextAssembler、PrivacyPolicy 和 TokenBudget。
- 流式预览、取消和错误归一化。
- AiProposal 的接受、部分接受和拒绝。
- 续写、重写、润色和摘要。

验收：AI 失败不影响正文；AI 输出不能直接成为修订；Key 不进入前端回读、项目数据库和日志。

### R4：故事设定和日常可靠性

交付：

- Character、Location、Faction、Item、Concept。
- EntityRevision、别名、标签和归档。
- SQLite FTS5 搜索和重建。
- 章节、人物和设定的多精度摘要材料，以及风格规则卡和写作技巧卡的基础管理。
- 简单持久化 Job Runner。
- 完整备份、恢复到新目录和项目健康扫描。
- 启动恢复和隐私安全的诊断包。

验收：系统达到本机日常长期使用标准；正文、规划和实体可搜索；备份恢复后关键哈希一致。

### R5：知识治理和章节定稿

交付：

- Relation、Fact、Event、Belief、Foreshadowing 和 EvidenceAnchor。
- AI 结构化输出验证。
- ChapterChangeSet 和 ChangeItem 审核。
- 冲突检测和高风险人工确认。
- KnowledgeVersion、WorldState 基础投影。
- AI 双输出 Schema、事实使用报告、不确定项、新设定候选和独立审核调用。
- FinalizationRecord 和替代定稿。
- 定稿事务、审计和 Outbox。

验收：知识候选不能绕过人工审核；定稿全部成功或全部失败；正式事实可追溯到正文证据和定稿记录。

### R6：按需高级能力

达到明确需求或性能触发条件后，逐项实施：

- Tantivy 全文索引。
- Embedding、向量索引和混合检索。
- 高级 ContextAssembler。
- 上下文规划 AI、按场景生成与状态接续、多角色生成和审核工作流。
- 完整 Task Runtime 和独立 Worker。
- 版本化 Workflow Runtime 和工作流画布。
- 时间线、关系图、伏笔和节奏分析。
- LARGE/STRESS 数据集性能工程。
- 全书一致性扫描。

这些能力互不要求一次全部激活，每项都必须有独立 ADR、基准和验收报告。

### R7：可选扩展

- Markdown、DOCX、EPUB、PDF 等导入导出。
- 声明式 Prompt、实体和工作流模板。
- 多窗口。
- 项目交换包。

账号、云端托管、多人协作、商业订阅、任意代码插件和公网遥测继续不属于当前范围。

## 13. 每项功能的统一实现步骤

后续功能默认使用五步模板：

1. 定义领域规则、输入输出和错误；只有复杂领域才建立独立聚合设计文档。
2. 实现 Application Handler、Repository Port 和短事务。
3. 暴露 typed Tauri API，生成 TypeScript 类型和客户端。
4. 实现 UI 的加载、空、成功、冲突、错误和恢复状态。
5. 完成领域测试、真实 SQLite 集成测试和关键交互测试，再更新 FeatureCatalog。

只有存在真实需要时增加：

- 跨域或异步响应：增加 Event 和 Outbox。
- 不可信结构化边界：增加 JSON Schema/Zod。
- 长时间操作：增加持久化 Job。
- 多种实现：增加 Port 和 Adapter。
- 两个以上独立消费者：拆共享 crate/package。
- 已测得性能问题：增加缓存、外部索引或 Worker。

## 14. 复杂能力引入门槛

| 能力 | 引入门槛 |
| --- | --- |
| 独立 Blob Store | SQLite 项目达到已定义规模并出现可复现的备份、读取或空间问题 |
| Tantivy | FTS5 未达到基准，或需要其分词、评分和异步索引能力 |
| 向量检索 | 已有稳定 EvidenceAnchor、来源版本和可评估的召回数据集 |
| 通用 Command/Query Bus | 出现动态模块、跨进程协议或大量统一中间件需求 |
| 完整 Registry 系统 | 出现动态发现或第三方声明式扩展需求 |
| 完整 Task Runtime | 至少有多个需要恢复、Checkpoint、租约或资源治理的长任务 |
| 独立 Worker | 任务会显著阻塞桌面进程、占用大量内存或需要故障隔离 |
| Workflow Runtime | 已有稳定 Command、持久化 Job 和至少三个真实重复工作流 |
| ReviewCase | ChangeSet 内审核无法满足批量队列或多来源治理需求 |
| 多窗口 | 已解决项目锁、同章节并发和跨窗口事件同步设计 |

## 15. 持续质量要求

每个阶段必须更新：

- FeatureCatalog 状态。
- 数据库 Migration 清单。
- 已知限制和风险登记。
- 阶段验收报告。
- 关键恢复和备份测试结果。
- 新增或修改的 ADR。

持续检查：

- Domain 没有依赖 Tauri、rusqlite、reqwest 和前端类型。
- React 没有直接访问数据库、模型接口和项目内部文件。
- ManuscriptRevision 历史内容不可更新或删除。
- AI Proposal 不能直接写正式正文和正式知识。
- 日志、错误和诊断不包含 Key、正文全文、完整 Prompt 和完整模型响应。
- 所有正式知识变化可追溯到来源、审核决策和知识版本。
- 所有可重建投影都具有重建测试。

## 16. 修订决策摘要

## 17. 正式开发起点

从本文件生效后，按以下顺序启动开发：

```text
01. 将三份设计文档纳入版本控制
02. 建立 Cargo、pnpm 和 Tauri Workspace
03. 建立 domain/application/infrastructure 三个 crate
04. 建立 React AppShell 和 typed Tauri IPC 验证
05. 固定 Rust、Node、pnpm、Tauri 和 SQLite 版本
06. 建立 SQLite Migration、PRAGMA 和 Health Query
07. 建立统一错误、强类型 ID 和 FeatureCatalog
08. 实现 CreateProject/OpenProject/CloseProject
09. 完成项目创建失败回滚和重复打开测试
10. 验收 R0 后进入 R1 规划领域
```

在 R0 完成前，不开始工作流、向量检索、关系图、通用插件、完整 Task Runtime 或完整知识治理实现。
