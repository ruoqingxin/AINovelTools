# ADR-002：渐进式共创体验修订

- 日期：2026-09-14
- 状态：Proposed
- 适用阶段：R5.1 体验校准；不自动开启 R6
- 关联文档：
  - `doc/总/渐进式AI小说共创工具设计讨论稿.md`
  - `doc/总/修订版设计与实施路线.md`
  - `doc/后续流程/README.md`
  - `doc/R5/R5 ADR-001知识证据与定稿边界.md`

## 1. 背景

R0-R5 已经形成了项目、规划、正文修订、AI Proposal、实体库、知识候选、证据锚点、人工审核和知识定稿的工程骨架。R5 在 2026-09-02 已通过自动化验收，R6 当前仍处于暂停状态，等待完整体验反馈。

现有产品的主要问题不是缺少模块，而是部分流程仍偏向“先完成规划，再开始写作”：作品设定中的核心项完成度会影响大纲和正文入口，知识候选虽然已经存在，但尚未成为正文工作区中的自然闭环，AI 上下文也主要围绕规划文本组织。

这会与渐进式共创的产品原则产生偏差：未知应当是有效状态，角色卡和完整大纲不应成为写作门槛，AI 只能提出候选，正文应当持续沉淀为可追溯知识。

## 2. 决策摘要

本 ADR 不推翻 R0-R5 的领域模型和可靠性约束，先通过一个 R5.1 体验校准阶段完成以下调整：

1. 规划完成度不再作为正文写作的硬性准入条件。
2. 规划项支持“未知、暂不决定、作者保留”等显式状态。
3. AI 产出统一遵循“生成 -> 候选/Proposal -> 作者决定 -> 正式内容”。
4. 正文保存后可以直接发起本章候选提取，提取结果进入审核或待定区。
5. 写作上下文优先提供当前章节和场景相关的正史切片，而不是整本资料库。
6. 增加同一作品内连续的 AI 共创讨论入口，讨论结果默认不进入正史。
7. 暂不引入向量检索、Tantivy、ReviewCase、独立 Worker 或完整 Workflow Runtime。

## 3. 采用原因

- 降低首次写作门槛，让工具从“一句话灵感”即可产生可编辑内容。
- 保留 R5 已建立的正文修订、证据、审核和定稿边界，避免可靠性倒退。
- 让资料库服务正文，而不是让作者为了维护资料库而中断创作。
- 先验证真实使用中的召回、审核和工作流问题，再决定是否进入 R6。

## 4. 需求修订

### 4.1 渐进式开始写作

系统必须提供两条并列入口：

- **一起规划**：进入现有规划工作台，逐步完善作品设定、主线、分卷和章节计划。
- **先写一段看看**：只需一句话核心，可选填写规模和第一卷方向，即可创建第一章或生成正文候选。

最低写作信息：

```text
一句话核心：必需
大致规模：可选，允许“先不定”
第一卷方向：可选，允许留白
```

以下内容不得作为开始写作的硬性前置条件：

- 主角完整背景
- 最终反派
- 力量体系完整定义
- 感情线
- 结局细节
- 完整世界观
- 完整角色卡

规划器中的“核心设定未完成”可以继续显示为建议、风险或下一步推荐，但不得阻断创建章节、保存草稿或生成第一段正文。

### 4.2 未知状态

规划项、设定项和候选内容必须能够区分至少以下状态：

```text
UNSET             尚未记录
UNKNOWN           明确未知
DEFERRED          暂不决定
AUTHOR_RESERVED   作者保留，不由 AI 决定
AI_SUGGESTED      AI 推测或建议
CONFIRMED         作者已确认
LOCKED            作者锁定
RETIRED           废弃或被替代
```

约束：

- 空内容不自动等于错误。
- `AI_SUGGESTED` 不得被当作正式事实、正式计划或正式实体。
- `UNKNOWN`、`DEFERRED` 和 `AUTHOR_RESERVED` 不得被模型自行补全为确定事实。
- `LOCKED` 内容只能通过作者发起的替代版本改变。

### 4.3 候选晋级状态机

所有 AI 生成的规划、正文、实体和知识内容都遵循统一的生命周期：

```text
GENERATED
  -> PENDING_REVIEW
      -> ACCEPTED
      -> PARTIALLY_ACCEPTED
      -> DEFERRED
      -> REJECTED
```

只有作者确认后，内容才能写入对应的正式对象：

- 正文候选 -> 编辑器草稿 -> `ManuscriptRevision`
- 规划候选 -> 正式规划修订
- 实体候选 -> `Entity` / `EntityRevision`
- 知识候选 -> `Fact`、`Relation`、`Event`、`Belief` 或 `Foreshadowing`

正式知识仍必须遵守 R5 ADR-001：候选、证据绑定、人工审核和定稿分步完成；AI 不得直接写入正式知识或 `WorldState`。

### 4.4 正文候选提取

章节保存新正文修订后，正文工作区应提供“提取本章候选”入口。首版允许作者手动触发，也可以在保存后给出非阻断提示；不得默认为每次保存自动创建大量待审核任务。

首批提取范围：

- 新角色、地点、势力、物品和概念
- 重要关系变化
- 新事实、事件和能力规则
- 角色状态变化和条件例外
- 潜在伏笔
- 与既有正式知识的冲突

提取结果必须绑定：

- 章节 ID
- 具体正文修订 ID
- block ID 和文本范围
- 原文哈希
- AI 生成记录或 Proposal ID

处理规则：

| 情况 | 默认行为 |
| --- | --- |
| 新增重要设定 | 提醒作者审核 |
| 重复印证既有设定 | 静默累计证据 |
| 潜在伏笔 | 放入待观察区 |
| 角色短期变化 | 标记为当前状态或条件例外 |
| 与正式知识冲突 | 高优先级提醒 |
| AI 推测 | 默认折叠，不进入正史 |

### 4.5 相关上下文切片

正文写作调用的上下文首版采用确定性查询和 SQLite 现有能力，不要求引入向量索引。上下文至少包含：

- 用户当前指令
- 当前章节和场景
- 当前章节执行卡和分卷规划
- 当前正文草稿或选区
- 与当前章节相关的正式实体
- 相关 Fact、Relation、Event、Belief 和 Foreshadowing
- 当前角色状态和知识边界
- 未揭示、未确认和作者保留内容的限制
- 最近相关章节摘要

上下文条目必须保留来源和版本。没有命中资料时，应明确告知模型“未检索到相关正式知识”，不得让模型声称已经读取完整故事设定。

上下文优先级：

```text
用户指令和当前选区
  > 当前章节目标与禁止事项
  > 已锁定正式知识
  > 已确认但可变化的设定
  > 当前状态、关系和伏笔
  > AI 建议、灵感和未决项
```

### 4.6 AI 共创讨论与剧情讨论

系统必须提供一个与当前作品绑定的连续讨论入口，用于：

- 讨论剧情方向和多个方案
- 质疑当前大纲或章节计划
- 发散角色动机、关系变化和冲突设计
- 比较不同的卷纲、节点或结局方向
- 询问“如果这样改，会影响什么”
- 将讨论中的内容整理为临时笔记、候选计划或候选设定

该功能与正文写作、规划生成使用同一作品上下文和模型配置，但职责不同：

```text
共创讨论：提出问题、方案和影响分析
规划生成：把作者选择的方向整理成候选规划
正文写作：根据已确认的上下文生成正文 Proposal
知识提取：从正文中提取有证据的候选知识
```

讨论结果不得直接修改以下正式对象：

- 正式正文修订
- 正式规划修订
- 正式实体和实体修订
- `Fact`、`Relation`、`Event`、`Belief`、`Foreshadowing`
- `KnowledgeVersion` 和 `WorldState`

讨论中的内容按以下层次处理：

```text
聊天消息
  -> 临时笔记（可选）
  -> 候选规划 / 候选设定 / 候选伏笔（可选）
  -> 作者确认
  -> 正式对象
```

首版交互要求：

1. 讨论会话属于当前作品，可以保留历史消息和上下文摘要。
2. 用户可以指定讨论范围：全书、当前卷、当前章节、当前场景或当前选区。
3. AI 回复应明确区分“已有正式内容”“讨论中的推测”“新建议”和“待作者决定”。
4. AI 可以提出多个方向，并说明每个方向的核心体验、收益、代价和受影响内容。
5. 用户可以将一条回复或其中一部分转为临时笔记、候选计划或候选设定。
6. 转换后的候选必须带有来源消息、上下文版本和创建时间，仍需作者确认。
7. 讨论不得因为资料不完整而强制补齐未知项；应允许 AI 建议“暂不决定”。

首版可以先采用轻量实现：在项目工作区提供“讨论剧情”面板或页面，复用现有 AI 请求、Proposal 保存和上下文组装能力；不要求先建设多角色聊天机器人、工作流画布或跨窗口会话治理。

## 5. 数据与实现边界

本 ADR 只规定语义和工作流，不要求立即重构数据库。

### 5.1 保留现有模型

继续使用现有：

- `Entity` / `EntityRevision`
- `Fact`、`Relation`、`Event`、`Belief`、`Foreshadowing`
- `KnowledgeCandidate`
- `EvidenceAnchor`
- `KnowledgeVersion` / `WorldState`
- `AiProposal`
- 不可变 `ManuscriptRevision`

不把所有内容立即合并成一个无结构的 `story_claims` 表。

### 5.2 允许的增量扩展方向

如果 R5.1 体验验证确认需要持久化统一语义，优先对现有候选或知识对象增加可迁移的元数据：

```text
story_state
author_commitment
truth_status
visibility
hardness
valid_from
valid_to
replaced_by
```

这些字段可以先落在候选层或独立元数据表，待使用稳定后再决定是否进入各正式领域对象。不得用展示层 `content_json` 作为唯一真值来源。

### 5.3 与现有项目的差异

现有项目已经具备本 ADR 所需的大部分可靠性基础，不需要从头建设新的数据层：

| 本 ADR 目标 | 现有项目基础 | 当前差异 |
| --- | --- | --- |
| 本地单机项目 | Tauri、SQLite、项目目录和备份恢复 | 无原则性差异 |
| 正文可回溯修改 | `ManuscriptRevision` 不可变追加 | 无原则性差异 |
| AI 结果先候选 | `AiProposal` 支持接受、部分接受和拒绝 | 需要把更多规划和提取结果接入同一边界 |
| 设定沉淀 | `Entity`、`EntityRevision`、Fact 和知识扩展 | 需要让正文成为自然入口 |
| 证据回溯 | `EvidenceAnchor` 和 `ClaimSource` 等现有证据机制 | 需要为正文提取自动创建并展示来源 |
| 相关上下文 | `context_store` 已检索 Fact、WorldState、Entity 和 Foreshadowing | 需要加入状态、可见范围和“未检索到”语义 |
| 渐进式写作 | 规划页已有直接编写和 AI 候选 | 写作准备度仍把设定、人物卡和章节卡作为阻断项 |
| 连续共创讨论 | 已有按任务区分的 AI 调用 | 尚无作品级持久化讨论会话和消息 |

因此，本 ADR 的主要交付不是新增模块数量，而是调整现有功能的组合方式：从“先完成规划再写作”改为“允许先写作，写作后逐步形成规划和设定”。

### 5.4 推荐改动顺序

按照价值、风险和返工成本，R5.1 应按以下顺序实施：

1. **先解除错误的写作阻断**：将人物卡、章节执行卡、完整世界观、结局和规划必填项改为建议；保留真正影响生成安全性的当前指令、已锁定内容和明确的正文版本边界。
2. **再打通正文到候选的纵向切片**：在正文工作区针对指定 `ManuscriptRevision` 提供“提取本章候选”，支持角色、地点、物品、事实、关系、能力、状态和伏笔候选，并展示正文证据。
3. **复用 R5 审核和定稿**：作者可以接受、编辑、延期、转伏笔或拒绝；正式写入仍经过现有 `EvidenceAnchor`、`ChapterChangeSet`、冲突检查和定稿事务。
4. **调整上下文切片**：继续使用 SQLite 确定性查询和 FTS5；只传当前章节相关的正式知识、当前计划、角色状态、伏笔和知识边界。
5. **增加轻量作品级共创讨论**：保存会话和消息，允许把讨论片段转换为临时笔记或候选内容；讨论默认不进入正史。
6. **最后再决定统一元数据**：根据真实使用中出现的重复状态和查询需求，为现有候选或正式对象增加 `story_state`、`visibility`、`hardness` 等字段。

该顺序的依据是：第一步直接解决产品定位偏差，第二步验证核心价值，第三步复用现有可靠性边界，后续两步再根据真实使用补足体验和语义模型。

### 5.5 首版候选实现边界

首版不把所有类型立即合并为新的 `story_claims` 表，也不要求一次实现全部实体类型的完整卡片编辑器。

推荐先以现有 `AiProposal` 作为生成记录，以一个带类型、负载、证据和候选状态的提取结果承载层保存待审核内容。批准时再转换为现有正式领域对象：

```text
正文修订
  -> ChapterExtractionProposal
  -> ExtractionItem[]
     - kind
     - payload
     - evidence_anchor_ids
     - status
  -> Entity / Fact / Relation / Event / Foreshadowing
```

如果现有 `KnowledgeCandidate` 只能表达 Fact，不能为了复用而把角色和伏笔伪装成 Fact。此时可以增加轻量的提取候选表或扩展 ChangeItem，但必须继续复用现有证据、审核、定稿和审计边界。

### 5.6 文档和版本基线

实现前必须先统一阶段文档与运行时代码的版本记录。当前 R5 验收和迁移文档记录的 schema version 与运行时代码中的 `CURRENT_SCHEMA_VERSION` 存在差异，应先确认这些迁移属于哪个阶段，再更新 R5/R6 记录和 Migration 清单。

该问题不改变本 ADR 的产品决策，但如果不先处理，会导致后续迁移、验收和回滚依据不一致。

## 6. 非目标

本 ADR 不包含以下内容：

- 向量数据库或混合检索
- Tantivy 全文索引
- 跨章节 `ReviewCase` 批量审核
- 独立 AI Worker
- 完整任务运行时、租约和检查点
- 多角色 AI 工作流界面
- 时间线、关系图和全书分析
- 本地模型部署入口
- Markdown、DOCX、EPUB、PDF 全套导入导出
- 云端同步、多用户协作和账号系统
- 一开始就把角色、事实、计划、关系和伏笔重构为统一 `story_claims` 真值表
- 要求用户先完成完整作品蓝图、角色卡或卷纲才能开始正文

这些能力仍按 `doc/后续流程/README.md` 和 `长期按需能力与延期项.md` 的阶段门禁管理。

## 7. R5.1 验收标准

### 7.1 写作入口

- 新建项目后可以只填写一句话核心并创建第一章。
- 未完成完整作品设定时，仍可保存正文草稿和正文修订。
- 规划建议可以提示缺口，但不能阻断普通写作。
- “一起规划”和“先写一段看看”两条路径都能回到同一个正文和知识体系。
- 用户可以在当前作品中连续讨论剧情，并从讨论结果创建候选内容。
- 新建作品后，最小可用路径不依赖人物卡、章节执行卡或完整规划；这些内容只作为相关建议显示。
- 规划页可以保留 15 个规划项，但不得把“下一项”或完成百分比作为写作阻断依据。

### 7.2 状态语义

- 未知、暂不决定、作者保留和 AI 建议可以被单独显示和持久化。
- AI 建议不会出现在正式知识或正式世界状态中。
- 锁定内容的修改会形成新版本并保留历史。

### 7.3 正文到知识

- 用户可以针对指定正文修订发起候选提取。
- 每条候选都有可打开的正文证据锚点。
- 候选可以被确认、编辑后确认、延期、转伏笔或拒绝。
- 重复事实不会强制生成重复审核任务。
- 高风险冲突不能绕过人工审核和定稿事务。
- 从正文提取的候选至少能覆盖一个新角色，并能编辑后创建 `Entity` / `EntityRevision` 或进入明确的待审核承载层。
- 重复印证已有内容时，系统优先增加证据，不重复制造同义待办。

### 7.4 上下文

- 正文生成至少能收到当前章节计划和相关正式知识切片。
- 上下文记录来源版本。
- 没有命中知识时不会虚构“已读取完整设定”。
- 上下文组装失败不会破坏正文、Proposal 或正式修订。

### 7.5 共创讨论

- 讨论消息和会话可以与当前作品关联并回看。
- 讨论内容不会直接写入正式正文、正式规划或正式知识。
- 用户可以选择一段讨论结果转为临时笔记或候选内容。
- 候选内容能够回到已有的作者确认、审核和定稿流程。
- AI 能够明确区分正式依据、推测和建议，不把讨论假设描述成既成事实。

### 7.6 可靠性回归

- 不可变正文修订、恢复和乐观并发行为保持不变。
- AI Proposal 接受后仍需经过编辑器草稿和正式保存。
- 知识定稿仍为原子事务。
- 备份、恢复、隐私和 Secret Store 约束不降低。

## 8. 后续行动

在开始实现前，必须按 `doc/后续流程/README.md` 完成阶段门禁，并明确以下事项是否纳入本阶段：

1. 更新 R5.1 开发清单和验收记录。
2. 为写作准入、未知状态和候选状态机补充领域契约测试。
3. 为正文“提取本章候选”补充 IPC、SQLite 和前端交互测试。
4. 为相关上下文切片补充来源、版本和 TokenBudget 测试。
5. 更新 FeatureCatalog，将新增能力标记为 `PARTIAL`，未完成能力不得显示为已实现。
6. 体验 R5.1 后，再依据真实数据决定是否申请进入 R6 单项能力。
7. 首先完成“只填写一句话核心 -> 创建章节 -> 保存正文 -> 提取候选角色 -> 作者确认 -> 后续上下文回用”的最小闭环，再扩展其他候选类型。
8. 在更新 FeatureCatalog 前，明确区分“已有底层能力”“已接入正文工作区”和“仍未实现”，不得用已有后台命令冒充完整用户流程。

## 9. 待决问题

以下问题不阻塞 R5.1 设计，但必须在对应功能实现前确定：

- 本章候选提取默认手动触发，还是保存后提供一次性建议。
- “继续观察”的候选是否需要单独的生命周期，还是映射为 `DEFERRED`。
- 角色当前状态、稳定倾向和条件例外是否在 R5.1 先以候选元数据表达。
- 章节完成度和项目首页的进度指标采用字数、章节、阶段还是区间估算。
- 正文提取是否允许作者选择“只提取新增内容”或“同时检查冲突”。

## 10. 结论

接受本 ADR 后，产品的下一步不是继续扩大模块数量，而是把现有 R0-R5 能力组织成真正的渐进式创作闭环：

```text
一句话灵感
  -> 可选规划
  -> 正文草稿
  -> Proposal / 候选
  -> 作者确认
  -> 正式正文和知识
  -> 相关上下文继续写作
```

核心不变量保持不变：

> 未知可以保留，计划可以变化，AI 可以提议，只有作者能够批准正史。
