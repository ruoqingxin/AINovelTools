# 一致性审核声明证据化实施文档

## 文档状态

- 日期：2026-09-15
- 状态：阶段 1-5 已实施，等待验收
- 实施记录：阶段 1-5 已按本文分阶段提交
- 适用范围：章节工作区的“创作准入”、正文工作区的“正文审核”
- 实施策略：先交付精简可用版本，同时保留规则引擎、证据解析和审核编排扩展接口
- 非目标：本版本不实现通用规则 DSL、任意表达式执行、完整推理引擎或跨作品规则市场

## 1. 背景

当前一致性审核的问题是审核输入范围过宽。正文审核和创作准入共用同一个后端动作与上下文组装流程，一次请求同时携带当前正文、完整章节执行卡、分卷规划、正式设定、事实、世界状态、实体、关系、角色认知、伏笔、摘要、事件和关键词检索结果。

这会产生三个问题：

1. 作品越长，审核请求越大。
2. 真正重要的硬约束容易被低价值资料淹没。
3. 同一正文可能因为每次召回的资料不同而得到不同结论。

本方案不再采用“全文对全文审核”，改为：

```text
审核目标
  -> 提取可验证声明
  -> 定位最小必要证据
  -> 确定性规则优先裁决
  -> LLM 复核语义与隐含冲突
  -> 合并为带依据的审核报告
```

## 2. 产品原则

1. 作者保留最终控制权，审核结果不得自动修改正文或正式知识。
2. 事实冲突和创作建议必须分开，创作建议不得阻断正文生成。
3. 没有正式证据时必须返回 `UNKNOWN`，不得让模型凭常识补设定。
4. 每条裁决必须能追溯到声明、证据来源和规则或模型来源。
5. 审核页签拥有全部审核操作，其他页签只负责展示状态和跳转。
6. 第一版采用固定类型规则，不实现通用规则语言，但接口必须允许后续增加规则类型、证据来源和裁决器。

## 3. 审核页签职责

### 3.1 章节工作区“创作准入”

该页签只处理创作前的计划审核。

页签内负责：

- 选择或确认审核模型和项目覆盖参数。
- 发起或重新发起创作准入。
- 查看运行中状态并取消任务。
- 查看准入结论。
- 查看声明、引用证据、规则命中和无法确认项。
- 查看哪些正式资料缺失。
- 跳转到章节执行卡、人物卡或作品设定处理问题。
- 关闭、拒绝或重新打开准入报告。

审核目标：

```text
这份章节执行卡是否允许进入正文创作阶段？
```

### 3.2 正文工作区“正文审核”

该页签只处理已成稿正文的一致性检查。

页签内负责：

- 选择或确认审核模型和项目覆盖参数。
- 发起或重新发起正文审核。
- 查看运行中状态并取消任务。
- 查看正文声明对应的正式证据。
- 查看 `BLOCK`、`WARNING`、`NOTICE`、`UNKNOWN` 和 `PASS` 结果。
- 跳转到正文、人物卡、设定或知识记录处理问题。
- 关闭、拒绝或重新打开正文审核报告。

审核目标：

```text
这段已经写出的正文是否违反了已确认事实或正式约束？
```

### 3.3 其他页签的边界

- “创作准备”只负责列缺口和导航，不发起审核。
- “AI 创作”遇到审核阻断时只显示原因和“前往创作准入处理”链接，不提供发起审核按钮。
- “候选区”只处理正文候选的采用、放弃和对比，不承载一致性审核。
- “知识提取”只处理正式正文到知识候选的提取与采用。
- 审核运行状态继续以 AI 运行记录为准，切换页签不得重置。

## 4. 第一版范围

### 4.1 正文审核声明类型

第一版只覆盖以下六类高价值声明：

| 类型 | 示例 | 主要证据 |
|---|---|---|
| `CHARACTER_STATUS` | 某角色死亡、失踪、在场或已公开身份 | 人物卡、事实、事件 |
| `CHARACTER_LOCATION` | 某角色当前位于某地点 | 当前世界状态、事实、事件 |
| `ABILITY_OR_REALM` | 某角色使用能力、突破境界或越过能力边界 | 人物事实、固定属性、硬规则 |
| `ITEM_POSSESSION` | 某角色持有、使用或消耗关键物品 | 物品实体、事实、事件 |
| `RELATION` | 师徒、敌对、婚约、阵营关系 | 关系记录、人物卡 |
| `KNOWLEDGE_BOUNDARY` | 某角色说出或表现出不应知道的信息 | 角色认知、事件参与记录 |

### 4.2 创作准入声明类型

创作准入第一版覆盖：

| 类型 | 示例 |
|---|---|
| `REQUIRED_EVENT` | 本章必须发生守门冲突 |
| `FORBIDDEN_EVENT` | 本章不得揭露师兄真实叛变原因 |
| `ALLOWED_CHARACTER` | 本章允许出现的角色 |
| `STAGE_BOUNDARY` | 本章不得突破至筑基 |
| `FORESHADOWING_WINDOW` | 某伏笔必须或不得在本章推进 |
| `PLAN_DEPENDENCY` | 本章依赖的前置事件尚未发生 |

### 4.3 第一版规则类型

第一版不提供通用规则脚本，只实现固定、可测试的规则类型：

| 规则 ID | 判定 |
|---|---|
| `NARRATIVE_PERSON_CONFLICT` | 正文叙述人称与锁定设定冲突 |
| `ENTITY_NOT_ACTIVE` | 已归档或失效实体仍以正常角色出现 |
| `FACT_OBJECT_CONFLICT` | 同一主体、同一规范谓词出现互斥结论 |
| `LOCATION_CONFLICT` | 同一时间窗口出现互斥位置 |
| `ABILITY_UNCONFIRMED` | 能力使用没有正式解锁证据 |
| `ITEM_OWNERSHIP_CONFLICT` | 使用未持有、已消耗或归属冲突的物品 |
| `RELATION_CONFLICT` | 正文关系与正式关系互斥 |
| `KNOWLEDGE_BOUNDARY_SUSPECTED` | 存在明显的信息边界风险，进入模型复核 |
| `CHAPTER_FORBIDDEN_EVENT` | 出现章节合同明确禁止的事件 |
| `CHAPTER_REQUIRED_EVENT_MISSING` | 缺少章节合同明确要求的事件 |

无法可靠结构化的判断保持为 `UNKNOWN` 或交给 LLM，不得为了规则命中而强行解释自然语言。

## 5. 总体架构

### 5.1 分层

```text
Frontend review tab
  -> Tauri command
  -> ConsistencyReviewService
      -> ReviewScopeBuilder
      -> ReviewClaimExtractor
      -> ReviewEvidenceResolver
      -> DeterministicReviewEvaluator
      -> SemanticReviewAdjudicator
      -> ReviewReportMerger
      -> ReviewTraceStore
  -> AiProposal / AiProposalReview
```

### 5.2 扩展接口

第一版使用具体实现，但按接口边界组织，后续可以替换或增加实现。

```text
ReviewScopeBuilder
  根据 reviewPurpose 生成审核目标与基准，不返回无关全局资料

ReviewClaimExtractor
  从正文或执行卡中提取声明，返回原文块和文本范围

ReviewEvidenceResolver
  按声明中的主体、别名、类型和时间线索获取最小必要证据

DeterministicReviewEvaluator
  执行固定规则，返回结构化规则命中

SemanticReviewAdjudicator
  只查看单条或小批声明及对应证据，负责语义复核

ReviewReportMerger
  合并规则与模型结果，统一严重程度、去重和排序

ReviewTraceStore
  保存声明、证据、规则命中、模型裁决、遗漏项和模型阶段调用记录
```

接口应接受稳定领域对象，不直接接受 SQLite 行、Tauri 参数或前端 JSON。

## 7. 持久化

第一版建议只增加一张审核轨迹表，避免把声明和证据拆成多张表造成过度设计。

当前数据库基线为迁移版本 41，本文按 42 预留审核轨迹表；实施时仍以实际 `CURRENT_SCHEMA_VERSION` 为准，如期间已有新迁移则顺延编号。

```sql
CREATE TABLE ai_review_traces (
    run_id TEXT PRIMARY KEY NOT NULL,
    review_purpose TEXT NOT NULL,
    chapter_id TEXT NOT NULL,
    target_revision_id TEXT,
    context_version TEXT NOT NULL,
    claims_json TEXT NOT NULL CHECK(json_valid(claims_json)),
    evidence_json TEXT NOT NULL CHECK(json_valid(evidence_json)),
    deterministic_findings_json TEXT NOT NULL CHECK(json_valid(deterministic_findings_json)),
    model_findings_json TEXT NOT NULL CHECK(json_valid(model_findings_json)),
    omitted_items_json TEXT NOT NULL CHECK(json_valid(omitted_items_json)),
    stage_requests_json TEXT NOT NULL CHECK(json_valid(stage_requests_json)),
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);

CREATE INDEX idx_ai_review_traces_chapter_purpose
    ON ai_review_traces(chapter_id, review_purpose, created_at DESC);
```

关联方式：

- `ai_review_traces.run_id` 对应 `ai_tasks.id`。
- `ai_proposals.task_id` 对应同一次审核运行。
- 旧审核没有轨迹时，审核报告仍可展示，但不显示声明和证据层。

## 8. 审核上下文

### 8.1 通用内容

两个审核都始终携带：

- 固定且精简的任务合同。
- 作者锁定或确认的硬规则。
- 审核用途。
- 当前章节合同或执行卡。
- 审核模型参数摘要，不发送密钥。

`UNKNOWN`、`DEFERRED`、`AUTHOR_RESERVED` 和 `AI_SUGGESTED` 不得作为硬冲突依据。

### 8.2 创作准入上下文

默认携带：

- 当前章节执行卡。
- 本卷阶段目标和本章依赖。
- 本章涉及角色的当前状态摘要。
- 本章相关伏笔窗口。
- 作者锁定硬规则。

默认不携带：

- 正文历史全文。
- 全部旧章节摘要。
- 全部正式设定长段落。
- 与本章无实体、事件或伏笔关联的全局资料。

### 8.3 正文审核上下文

固定携带：

- 待审核正文。
- 当前章节执行卡。
- 作者锁定硬规则。

按声明追加：

- 声明涉及的主体和正式实体。
- 与主体直接相关的事实和当前状态。
- 关系、角色认知和参与者事件。
- 明确命中的能力、物品、地点和伏笔记录。
- 必要时命中的历史摘要，只作为参考，不作为铁证。

默认不携带：

- 完整分卷规划。
- 全部全局摘要。
- 全部事件。
- 与声明无关的关键词检索片段。

### 8.4 上下文预算

- 超过输入预算时必须按声明分组截断，并记录 `omittedItems`。
- 不允许静默截断全部高优先级硬规则。
- 截断后不得把未发送内容描述成“已审核”。
- 审核报告必须显示“有 N 项因上下文预算未完成检查”。

## 9. 实施流程

### 9.1 发起审核

1. 校验作品、章节、审核用途、正文修订和模型配置。
2. 计算用途对应的 `contextVersion`。
3. 创建统一 AI 运行记录，状态为 `RUNNING`。
4. 写入审核用途和运行阶段元数据。
5. 发出 `ai-task-started` 事件。

### 9.2 构建审核目标

`ReviewScopeBuilder` 根据用途生成最小输入：

- `ADMISSION` 以执行卡和阶段约束为目标。
- `MANUSCRIPT` 以当前正文为目标。

### 9.3 提取声明

1. 将正文按编辑器块切分。
2. 使用严格 JSON 输出提取声明。
3. 每条声明必须带逐字 `quote`、`blockId` 和重要性。
4. 使用现有正文定位能力计算文本范围。
5. 无法定位的声明丢弃并计入 `omittedItems`。
6. 长章节按块分批提取，最后去重合并。

声明提取不得直接判冲突，只回答“正文做出了哪些值得核对的事实声明”。

### 9.4 定位证据

按声明类型查询：

| 声明 | 查询顺序 |
|---|---|
| 人物状态 | 实体当前版本、状态事实、最近相关事件 |
| 当前位置 | 当前世界状态、位置事实、最近移动事件 |
| 能力或境界 | 人物固定属性、事实、硬规则 |
| 物品 | 物品实体、归属事实、消耗或遗失事件 |
| 关系 | 正式关系、关系双方实体 |
| 知识边界 | 角色认知、参与者事件、角色已知事实 |
| 章节合同 | 结构化合同或执行卡解析结果 |

证据选择规则：

1. 先按实体名称和别名精确匹配。
2. 再按声明中的主体和目标词匹配。
3. 不按章节标题做泛化召回。
4. 每条声明默认只保留 3 到 8 条最高权威证据。
5. 找不到证据时返回 `UNKNOWN`，不得扩大召回整个作品。

### 9.5 确定性规则

1. 规则只评估已经解析出的声明和最小证据。
2. 规则结果必须引用 `ruleId`、`claimId` 和 `evidenceIds`。
3. 规则无法可靠判断时返回“不裁决”，不得返回失败。
4. 多条规则命中同一问题时按规则 ID 去重。

### 9.6 LLM 语义复核

LLM 只接收：

- 当前声明。
- 与该声明相关的证据。
- 固定输出合同。

建议按小批处理，例如每次 5 到 10 条声明。不得重新注入全作品上下文。

LLM 负责：

- 语义等价但形式不同的冲突。
- 隐含能力、物品或知识边界。
- 两段描述是否属于同一事件的不同表述。
- 角色行为是否违反已确认动机。

### 9.7 合并结果

1. 规则结果优先。
2. LLM 结果不得降低规则明确给出的 `BLOCK`。
3. 相同声明、相同证据和相同问题去重。
4. 没有证据的 LLM 结论自动降为 `UNKNOWN` 或 `NOTICE`。
5. 汇总一个总 verdict，但保留所有逐条 finding。
6. 保存审核轨迹，再完成 `AiProposal`。

## 10. 报告与前端展示

审核报告按以下顺序展示：

1. 总结。
2. `BLOCK`。
3. `WARNING`。
4. `NOTICE`。
5. `UNKNOWN`。
6. 因预算或解析失败未检查的项目。

每条 finding 显示：

- 声明原文。
- 问题说明。
- 正式依据。
- 证据来源等级。
- 规则来源或模型来源。
- 修改建议。
- 定位到正文块或知识记录的入口。

两个审核页签必须按 `reviewPurpose` 过滤结果：

- 创作准入只显示 `ADMISSION` 报告。
- 正文审核只显示 `MANUSCRIPT` 报告。
- 某一用途关闭报告后，不得影响另一用途。
- 只有 `ADMISSION` 报告参与写作准入判断。

## 11. 接口建议

### 11.1 发起审核

```text
run_consistency_review({
  reviewPurpose,
  profileId,
  chapterId,
  chapterTitle,
  chapterPlan,
  volumePlan,
  documentJson,
  temperature?,
  maxOutputTokens?
})
```

返回统一的运行任务标识和最终 `AiProposal`。

### 11.2 查询结果

```text
list_ai_proposals(chapterId, reviewPurpose?)
get_consistency_review_trace(proposalId)
```

### 11.3 运行控制

继续复用：

```text
list_ai_runs(limit)
cancel_ai_task(taskId)
```

审核运行态继续从持久化 AI 运行记录恢复，不能在页签卸载时丢失。

AI 运行记录需要保留每次审核阶段调用的请求快照、模型与参数摘要、响应解析结果和降级记录；正文与敏感密钥按现有脱敏规则处理，不得只保留最终汇总结果。

## 12. 实施阶段

### 阶段 1：用途拆分与页签收口

- 为审核增加 `reviewPurpose`。
- 拆分 `ADMISSION` 和 `MANUSCRIPT` 的上下文构建。
- 新增按用途过滤的审核结果。
- 保证只有准入报告影响写作准入。
- 将全部审核按钮、取消、重跑、关闭操作收口到审核页签。
- AI 创作页只保留阻断提示和跳转。

阶段出口：两个审核完全独立，正文审核不再影响写作准入。

### 阶段 2：最小声明与证据流程

- 新增审核轨迹存储。
- 实现固定 JSON 声明提取。
- 实现实体名称和别名解析。
- 实现六类声明的定向证据查询。
- LLM 改为只查看声明和证据。
- 前端显示声明与依据。

阶段出口：一次审核不再加载完整项目知识，报告可解释。

### 阶段 3：固定规则

- 实现第一版固定规则 ID。
- 规则结果与 LLM 结果合并。
- 增加 `UNKNOWN` 和未检查项展示。
- 建立规则回归样例。

阶段出口：明显硬冲突可以稳定阻断，误判可以追溯到具体规则和证据。

### 阶段 4：创作准入合同化

- 为章节执行卡生成可缓存的结构化合同视图。
- 支持必须事件、禁止事件、允许人物、时间窗口和阶段边界。
- 作者确认后才把合同字段用于阻断。
- 保留自由文本执行卡，不强制立即迁移编辑方式。

阶段出口：创作准入可以执行确定性的章节合同检查。

### 阶段 5：扩展接口稳定

- 允许增加新的 `ReviewClaimType`。
- 允许增加新的 `ReviewEvidenceResolver` 来源。
- 允许增加新的规则类型，但仍不引入通用脚本。
- 预留规则版本、作用域、优先级和生效时间字段的设计位置。

## 13. 测试要求

### 13.1 领域和规则

- 用途、声明、证据、severity 和 verdict 映射。
- 规则命中、未命中、证据不足和重复去重。
- 同一主体和规范谓词的互斥事实。
- 别名匹配和未匹配。
- 输入截断后的遗漏统计。

### 13.2 数据库

- 空库迁移。
- 已有项目迁移。
- 旧审核默认映射为 `ADMISSION`。
- 轨迹写入、读取和删除项目清理。
- JSON 约束和索引。

### 13.3 审核流水线

- 正文审核和创作准入使用不同 context version。
- 正文审核报告不参与写作准入。
- 无证据时返回 `UNKNOWN`，不得返回 `BLOCK`。
- LLM 不能降低规则明确的 `BLOCK`。
- 取消任务后的状态和错误码。
- 主模型失败后的 fallback 记录。

### 13.4 前端

- 创作准入操作只出现在“创作准入”页签。
- 正文审核操作只出现在“正文审核”页签。
- 两页签不会显示对方的报告。
- 切换页签后运行状态和取消按钮仍正确。
- 报告中的声明、证据和 unknown 可展开查看。
- 运行、空、失败、过期、取消和完成状态完整。

## 14. 验收标准

满足以下条件才认为第一版完成：

1. `ADMISSION` 和 `MANUSCRIPT` 从请求、上下文、报告、freshness 到准入判断完全分离。
2. 正文审核不会阻止或放行正文创作。
3. 创作准入仍遵守当前作品设定的严格或建议策略。
4. 审核请求默认只携带审核目标和按声明解析出的最小证据。
5. 没有正式证据时不判硬冲突，显示 `UNKNOWN`。
6. 最终报告中的每条 finding 都能查看依据来源。
7. 审核发起、重跑、取消、查看和关闭操作全部位于审核页签。
8. 切换页签后审核运行状态不会丢失。
9. 旧的未分类审核仍可查看，并保持原有准入行为。
10. Rust、SQLite、IPC、前端测试和迁移测试全部通过。

## 15. 非目标和延期项

第一版明确不做：

- 用户自定义规则表达式。
- 通用规则 DSL。
- 图数据库、时间线推导或因果推理引擎。
- 自动修改正文、自动关闭审核或自动采用知识。
- 向量数据库和全文语义召回重构。
- 为所有自然语言谓词建立完整本体。
- 把全部历史摘要变成硬冲突依据。

这些能力只能在下述条件满足后评估：

- 现有六类声明和固定规则无法覆盖真实问题。
- 已有评测样本能证明需要更强推理。
- 规则和证据接口不需要破坏现有数据兼容性。

## 16. 风险与处理

| 风险 | 处理 |
|---|---|
| 声明提取漏项 | 显示提取覆盖率；长章节分块提取；保留整章检查入口 |
| 实体别名匹配错误 | 使用实体别名表；低置信度不进入规则，交模型复核 |
| 自由谓词无法规范 | 只对固定规则使用规范谓词，其余交 LLM 处理 |
| 规则误阻断 | 规则必须给证据；第一版缩小规则范围；保留关闭和重新审核 |
| 两阶段调用成本增加 | 声明提取结果按正文修订和合同版本缓存；小批合并复核 |
| 旧报告无用途 | 默认映射为 `ADMISSION`；不回溯改变历史结论 |
| 输入预算截断 | 记录遗漏项；硬规则优先；报告明确显示未完成检查 |
| 前端双页签状态串用 | 查询键、上下文版本、报告过滤和准入判断全部带 `reviewPurpose` |

## 17. 最终实施边界

第一版要交付的是一条完整但克制的链路：

```text
审核页签发起
  -> 提取声明
  -> 定向查找正式证据
  -> 固定规则检查
  -> LLM 复核剩余语义问题
  -> 合并带依据的报告
  -> 作者处理或关闭
```

它不试图一次解决小说中的全部一致性问题，但会把审核输入从“整个作品”收缩为“少量声明和对应证据”，并为后续规则类型、证据来源、章节合同和版本化规则留下稳定接口。
