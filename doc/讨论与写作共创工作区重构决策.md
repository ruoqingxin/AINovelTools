# 讨论与写作共创工作区重构决策

日期：2026-10-22

补充修订：2026-10-22，增加创作质量、叙事位置、依据失效、并发指令、部分采用、运行审计及上线门槛。

状态：产品方向与重构原则已确认；具体技术选型、数据结构和性能数值需在实施设计中验证。

范围：讨论、按需检索、讨论记忆、设定与大纲共创、正文共创，以及它们之间的确认和变更流程。

本次交付：决策与设计文档，不包含业务代码改动。

## 1. 核心决策

讨论是本工具的核心工作流，不是独立聊天框，也不是写作前的一次性准备步骤。

重构后的目标是一个统一的小说共创工作区：

> 聊的时候懂稿，写的时候懂书，修改的时候记得作者已经决定了什么。

作者可以在同一条创作流程中讨论设定、调整大纲、查询已有资料、试写正文、局部改稿、选择版本并继续写作。系统负责检索、来源、记忆、版本和变更追踪，作者保留最终决定权。

本次重构以创作效果、上下文准确性、使用体验和长期可维护性为优先。不得为了兼容旧接口、旧数据结构、旧页面交互、旧提示词或旧流程而牺牲目标效果。

### 1.1 效果优先的含义

- 允许重新设计讨论领域模型、数据库结构、前后端接口、模型交互协议和工作区界面。
- 允许删除失去价值的旧抽象、入口、兼容层和重复流程，不要求长期维持新旧两套能力。
- 现有固定消息条数、资料数量、字符额度、整理流程和任务划分都不是不可更改的产品要求。
- 已有模块仅在确实符合新目标时复用，不因已经实现而保留。
- 不预设必须推倒所有基础设施。备份、事务、修订、编辑器等能力同样需要按实际价值评估。
- 不以提示词变长、附加资料变多或增加模型调用次数作为效果提升的替代指标。

### 1.2 效果优先不等于放弃数据安全

原始正文、作者设定、讨论记录和创作修订是作者资产，不能因“不兼容”被静默删除或错误转换。

允许采用一次性迁移、导入新格式、只读保留旧项目副本等方式替代运行时兼容。任何不可逆迁移必须先备份、说明影响并获得明确确认。新格式是否支持旧版程序打开，可以不作为目标，但必须在迁移前说明。

## 4. 目标与非目标

### 4.1 核心目标

1. 主动发现与本轮创作有关的已有设定、正文和历史决定。
2. 检索高相关内容，而不是把全书、全部设定和完整聊天历史塞进上下文。
3. 允许 AI 大胆创作、提出不同意见、主动查证和继续试写。
4. 区分依据、推测、新建议、作者选择和正式内容。
5. 长期记住最新决定、否定方案、未决问题和适用范围。
6. 在同一工作区完成设定、大纲、正文的讨论与编辑。
7. 对修改提供准确范围、可比较版本、撤销和来源追踪。
8. 让正式变更可确认、可追溯，重大影响不被静默遗漏。

### 4.2 不做的事情

- 不要求先填完人物卡、世界观或全书大纲才能开始创作。
- 不把创作伙伴做成每轮逐条审核设定的检查员。
- 不要求每个新点子都必须已经存在于资料库中。
- 不让 AI 未经授权自动重写全书、覆盖正式设定或提交正文。
- 不通过复杂表单、强制模式切换和频繁确认维持内部状态。
- 不把“绝不出现任何矛盾”作为无法验证的口头保证；用来源、校验、评测与纠错能力约束实际效果。
- 不在本次文档阶段确定模型供应商、向量服务或第三方技术栈替换。

## 5. 标准创作流程

### 5.1 发现已有设定并扩展

作者：“我想设计一个新境界。”

系统应识别可能涉及修炼体系，查找已有体系、当前有效规则及必要的关联资料。名称不同但含义相近的资料也应有机会被发现。

若找到已有资料，AI 可以回应：

> 目前《修炼体系》已有炼气、筑基、金丹三个阶段，并规定突破需要凝聚灵核。你想在现有体系上增加一个阶段，还是重新设计整套体系？也可以先试一个新版本，暂不替换旧设定。

行为要求：

- 先有实际检索依据，再声称“已有”。
- 展示相关要点，不倾倒整份资料。
- 新增内容不一定与旧规则冲突，兼容的扩展可以直接继续讨论。
- 需要取舍时再询问，不把所有创意都拦在“扩展还是重构”上。
- 支持沿用扩展、局部修改、另起版本探索，以及最终全面替换。
- 作者已经选择的重构方向不反复确认，除非出现新的重大影响。

### 5.2 从设定直接进入正文

作者：“放在金丹之后，突破代价是失去一段记忆。”

系统将这条明确选择记入当前讨论的决定，保留来源和范围；它不等于正式体系已经被替换。

作者：“拿主角突破写一段，压抑一点。”

系统读取当前工作稿、人物当前情况、叙事位置和相关规则，在稿件区形成正文草稿。未确定但不影响继续创作的细节可以合理创造，不要求作者先补齐资料。

作者：“前半段保留，后面改成他忘了母亲的声音。”

系统仅修改目标部分，不重写已经要求保留的文本，不擅自改动其他章节或正式设定。

### 5.3 从试写到正式采用

作者：“就采用这个，并更新境界设定。”

系统生成关联变更，说明正文与境界设定分别会如何修改，并列出直接已知的影响。作者可一次确认整组明确的正式变更，也可局部采用。

未同步的旧章节成为影响待办，不得声称已经修复全书。正文采用本身不等于从中提取的所有知识都已经通过事实审核。

## 6. 意图识别与执行权限

不要求作者手动选择内部任务类型。系统结合当前目标、选区、发言和对话状态理解意图。

| 作者表达 | 默认解释 | 默认行为 |
| --- | --- | --- |
| “如果突破会失忆呢？” | 探索假设 | 讨论可能性，不修改正式设定 |
| “先写一版失忆的看看。” | 试写 | 生成可继续编辑的候选工作稿 |
| “就确定突破会失忆。” | 当前方向选择 | 记录有范围的讨论决定，区分是否已正式确认 |
| “把这段结尾改掉。” | 修改当前工作稿 | 明确目标后直接修改，可撤销 |
| “前半段别动。” | 局部保护要求 | 约束本次及其连续修改，不扩大为全书规则 |
| “把寿命代价改成失忆。” | 替换既有规则的意图 | 识别目标与版本，准备明确的正式变更确认 |
| “采用这版并更新设定。” | 正式采用多个关联对象 | 展示范围和差异，一次确认关联变更 |
| “找出所有相关章节。” | 全范围查证 | 分批检索，交代范围、覆盖和未完成部分 |
| “换第二个。” | 指代历史方案 | 找回对应方案；无法唯一定位时简短询问 |

原则：

- 当前工作稿有明确修改指令且目标唯一时，不逐句弹窗确认。
- 正式内容的提交、替换和跨对象更新必须有明确授权与可见的变更范围。
- 作者指令已包含清晰的正式确认语义，且界面已经呈现准确差异时，不重复索要同一确认。
- 模糊赞许、假设、角色台词和试写不自动触发正式采用。
- 一次确认只授权当前目标、当前版本和当前变更，不形成未来无限写权限。
- 重大歧义、无法唯一定位的对象、受保护内容和新发现的高影响变更需要确认。

## 7. 统一工作区

### 7.1 主要界面

- 讨论区：交流、查询、方案比较、修改说明和必要追问。
- 稿件区：持续编辑当前设定、大纲或正文，支持作者与 AI 接续修改。
- 辅助区域：来源、讨论决定、未决问题、版本和影响待办，按需展开。

稿件不是聊天消息的副本。它有自己的目标、版本和编辑状态，能够跨多轮持续更新。

不以大量常驻面板和状态标签挤压写作空间；窄屏可以切换讨论与稿件视图，但不能失去任务关联。用户无需为了从讨论转到试写而重新建立会话或复制上下文。

### 7.2 必备交互

- 流式回复与生成进度，支持停止。
- 稿件局部选择、保留范围、局部采用、差异对比和撤销。
- 重试不覆盖上一次可用结果，不重复提交已生效变更。
- 从引用跳到对应原文和修订，不要求作者猜测资料来源。
- 生成期间允许继续手动编辑，并在冲突时保留双方版本。
- 切换讨论、稿件或项目后，不把迟到结果应用到新目标。
- 输入、工作稿和可恢复的生成结果不因界面切换或请求失败丢失。

### 7.3 创作伙伴的回应质量

- 先回应作者当前的问题与意图，不固定每轮列三个方向、追问问题或重述全部已有设定。
- 能指出方案薄弱处并给出理由和改进方向，不只附和；作者明确选择后，不反复推销被拒方案。
- 遇到真正影响当前创作的歧义时，优先询问最关键的问题；可以安全假设的小细节不阻塞试写。
- 讨论解释与可采用正文分开呈现，不把“这里建议增加冲突”等写作指导混入小说文本。
- 作者可以要求只讨论、不改稿，或只输出试写；讨论工作区的存在不构成每轮自动修改授权。

## 8. 状态与来源模型

以下是逻辑模型要求，不是最终数据库表结构。实现可以调整命名，但不能丢失这些语义。

### 8.1 必须区分的对象

| 对象 | 用途 | 边界 |
| --- | --- | --- |
| 原始讨论记录 | 保存作者与 AI 的实际表达 | 发言不自动等于决定 |
| 讨论决定 | 保存作者明确采用的方向 | 必须有范围、来源及替代关系 |
| 方案与分支 | 保存可比较、可继续的探索 | 未采用分支不污染正式内容 |
| 工作稿 | 承载设定、大纲或正文编辑 | 自动保存不等于正式提交 |
| 正式作者设定 | 保存作者确认的规则 | 不等于正文事件已经发生 |
| 正式正文与修订 | 保存作者采用的稿件 | 不等于所有叙述都是故事世界的客观事实 |
| 正文事实及角色知识 | 保存经审核的知识与知情边界 | 不由模型仅凭试写直接创建 |
| 变更集与影响待办 | 管理关联更新及未同步项 | 有范围，有版本，有执行记录 |
| 检索证据 | 绑定回复与实际阅读的材料 | 摘要、推测和原文不能混用身份 |

### 8.2 讨论决定的最低信息

- 内容、状态、作者表达来源及必要的方案引用。
- 所属项目、讨论或分支，以及适用对象和范围。
- 是否正式确认，生效条件和需要时的故事时间。
- 与旧决定的替代、撤回或冲突关系。
- 原始消息或修订定位，以及作者可编辑的纠正记录。

建议区分采用、否定、待定、已替代、已撤回。最终实现不必使用这些字面枚举，但必须避免被否定和已替代的方案重新冒充有效决定。

### 8.3 不使用单一权威排序解决所有问题

来源类别、是否确认、适用范围、故事时间、叙事视角和所在分支应分别表示。

“较新”不一定更正式；“正式设定”不能静默改写已有正文；“正文有这句话”也不等于客观事实。不同依据冲突时，保留差异并交给作者选择修订方向。

## 9. 每轮运行机制

建议采用可继续检索和核实的运行闭环，而不是一次拼接上下文后直接生成。

```text
作者输入 + 当前目标/选区/未保存工作稿
  -> 理解意图、指代和授权范围
  -> 读取相关有效决定与必要背景
  -> 检索命中及精确片段
  -> 必要时读取原文、补查条件和关联资料
  -> 形成自然回复、工作稿修改或待确认变更
  -> 验证来源、版本、修改范围及明显冲突
  -> 展示或应用授权内的结果
  -> 持久化结果、决定与执行来源
```

- 简单问题使用短路径，不强制每轮额外调用 AI 做检索规划、总结或全书校验。
- 复杂问题允许模型根据真实工具结果继续查证，不让它假装读过未提供的材料。
- 创作回复与结构化编辑操作可以在内部拆分，不要求作者阅读 JSON。
- 工具调用、稿件修改与最终回复共享运行标识，便于取消、重试和追踪。
- 达到预算或暂时无法查证时，保留已有结果，说明未完成范围，不伪造完整结论。

### 9.1 能力与权限

需要提供检索资料、读取原文、查找历史方案、读取有效决定、读取当前稿件、准备修改和提交已授权变更等明确能力。

工具的对象访问必须受项目、目标、分支和版本约束。正式写入权限由执行层校验，不能只依靠提示词约束。项目文本、引用文献和历史发言不是系统指令，不得借此扩大权限。

模型适配层应支持实现闭环所需的真实能力。不能因为旧模型调用接口只能一次输出文本，就把新工作流降级成模拟工具或假查询。具体提供商协议需在实施时验证。

### 9.2 任务快照与上下文记录

每次运行记录项目、分支、稿件目标、基础版本、选区、叙事位置，以及所采用决定和资料的实际版本。长任务可以分步读取不同版本，但必须记录变化并重新验证受影响结论，不能声称始终基于同一快照。

同时保留足够的上下文记录，用于解释“这次为什么引用了旧设定或漏掉了限制”：

- 区分检索命中、实际读取、实际送入模型和最终引用，不把候选列表当作模型已读材料。
- 记录预算裁剪、未覆盖范围、工具结果、模型与提示词版本，以及结构化操作的校验结果。
- 引用绑定到实际提供的原文和修订；不能仅凭模型生成的来源名称认定引用有效。
- 审计信息按需展开，提供依据和操作摘要，不要求保存或展示模型内部思维过程。

### 9.3 生成期间追加指令

“继续聊”和“继续手动改稿”是主工作流的一部分，不能用整段生成期间禁用输入来回避并发。

- 新消息有明确顺序与所属任务；系统应区分补充要求、取消当前任务和开启另一个任务。
- “等等，结尾不要死人”等新要求到达后，旧任务的自动应用资格必须先失效；再选择停止旧生成或将旧结果保留为备选。
- 不具备实时注入能力的模型可以停止后重启任务，不得假装已经把新指令传入正在进行的请求。
- 多任务结果不得按到达时间覆盖最新决定；只有目标、版本和指令状态仍有效的操作才能应用。
- 新增任务若会显著扩大费用，应说明；不得因补充一句话而无提示重跑整部长任务。

## 10. 检索与上下文策略

### 10.1 分开优化三个成本

1. 本地查找与资料读取成本。
2. 模型输入内容和推理成本。
3. 模型调用次数与端到端等待时间。

只缩短提示词不能证明检索性能已经优化；每轮增加多个模型请求也不能默认视为效果提升。

### 10.2 检索入口与顺序

- 直接指定的对象、选区和当前未保存工作稿属于必需工作上下文。
- 本轮明确提及或要求查找的资料优先，结合近期指代与有效决定补足查询。
- 支持名称、别名、关键词和语义相关性；具体索引与排序方案通过真实样例评测决定。
- 按需扩展到关联规则、限制、例外、依赖、人物当前状态和正文证据。
- 不因历史聊天更长或关键词重复更多就提高其事实地位。
- 旧 AI 方案可以用于恢复“第二个方案”等指代，必须保留其建议或废弃状态。
- 返回数量不足时不填充无关材料，也不通过固定少量结果假装完成穷尽查找。

### 10.3 先发现，再精读

优先返回可定位的命中摘要和来源信息，再读取回答所需的原文片段。摘要用于导航，不能替代证据。

规则片段应尽量保留完整的条件、限制和例外，不能截成相反含义。关键规则放不下时，应扩大预算、分轮处理或说明限制，不能悄悄裁掉。

### 10.4 索引、版本和缓存

- 建立随正文、设定、决定及相关资料变更而更新的索引，避免每轮全量扫描。
- 索引结果绑定来源修订；读取原文时再次核对有效版本。
- 新编辑尚未入索引时，应能直接读取对应当前目标，不用旧命中覆盖新内容。
- 缓存以项目、来源版本、查询条件和必要的分支范围为依据失效。
- 索引和摘要可重建，不能成为原始创作资料的唯一保存位置。
- 归档、替代、撤回、分支切换和秘密可见性变化应影响检索资格。
- 实体与稿件使用稳定身份关联，改名不切断引用；同名不同对象需要消歧，不能自动合并。旧名可作为明确标记的别名检索，不冒充当前名称。

### 10.5 覆盖范围与失败状态

必须区分未找到、未搜索、部分覆盖、索引待更新、资料读取失败和已经完成所声明范围内的查找。

用户要求查全时，应记录查找范围、资料版本快照、完成部分与未完成部分。只有明确范围内的候选源已经检查完，才可以声称完成该范围。搜索索引无命中本身不能证明全书绝对不存在。

### 10.6 预算按任务调整

普通交流、局部改写、全面查证和体系重构采用不同投入。优先保留本轮指令、修改目标、关键有效决定和直接相关规则。

不继承旧固定分配比例。检索、输入、输出和工具轮次需要预算及停止条件，防止无限查找；触及预算时提供继续、缩小范围或保留阶段结果的路径。明显超出常规的费用或耗时应提前提示。

保存容量与模型上下文容量分开管理。不能为了适应一次模型调用而截断、删除原始消息或稿件。

### 10.7 长任务的分段推进

多章生成、大范围改稿和体系整理可以按场景、章节或主题分步执行，每一步共享有效决定并记录已完成内容及未决项。计划是可调整的工作依据，不要求作者先写完完整大纲。

中断恢复应从已确认的执行检查点继续，核对期间新增的稿件和决定，不仅依赖一段自动摘要恢复整项任务。分段之间检查能力、代价、人物动机与情绪推进的连续性，避免每段单独合理、拼起来却互相矛盾。

## 11. 记忆、冲突与自由创作

### 11.1 记住决定，而非让作者维护聊天摘要

系统应从清晰表达中维护有效决定、被否定方案、未决问题和局部要求。模糊表达保留为候选，不猜成正式结论。

摘要和压缩记忆必须可回到原始表达；发生争议时能恢复原话和对应方案。作者可查看、纠正、撤回或删除记忆，删除后不得在后续检索中继续当作有效偏好。

同一讨论内部的决定可以直接服务连续试写。跨讨论共享时，应区分全书正式内容、作者明确共享的方向和仍在探索的局部决定，不自动合并互斥讨论。

### 11.2 不把一致性变成创作禁令

AI 可以创造未记录的人物细节、能力设想、场景和情节，提出不同意见，借鉴其他题材，并在必要时说明假设。

没有依据的新创意不能冒充旧设定，但无需给正文中的每个新句子附加“不确定”标签。来源说明和假设提示放在讨论或辅助信息中，不破坏小说阅读。

### 11.3 冲突判断需要条件

检查故事时间、适用对象、条件、分支、叙事真假和角色知情范围。人物成长、谎言、误解、传闻和故意误导不应被直接判为设定错误。

有可靠依据时指出具体差异；证据不完整时标记疑点，不把推测包装成冲突。作者主动重构后顺着新方向推进，同时保留未同步内容，不重复阻拦。

### 11.4 依据变化后的失效传播

原文被改写、规则被撤回、分支被放弃后，除索引与缓存外，引用这些内容的提取事实、状态、摘要、派生结论和影响待办也必须能定位并重新核对。

- 标记受影响内容为失效或待核对，不静默沿用，也不一律删除全部下游内容。
- 作者直接作出的决定与基于资料自动推导的结论分开处理。依据变了，不代表可以替作者撤销决定；应提示其依据变化，必要时重新确认。
- 纠正或删除记忆时，保留抑制其重新生效所需的撤回信息，避免旧消息被再次检索后自动重建同一错误记忆。
- 正文已采用但事实提取仍在审核时，可按原文检索并保留其叙事身份，不冒充已经审核的知识。

### 11.5 叙事位置与防止提前揭示

“人物当前状态”必须相对于正在创作的故事位置，不等于数据库里最新记录的状态。写早期章节时，不能直接套用人物后期能力、关系和知情程度。

任务需要区分创作时间、故事时间、叙事顺序和角色知情范围。倒叙、插叙、平行线和伏笔可以使用不同位置的资料，但不能因此自动提前揭露秘密或让角色全知。

作者层面的设定讨论可以参考后期真相；同一资料进入正文生成时，应按当前视角和揭示计划使用。必要时在讨论中提醒影响，不在正文里附加解释性免责声明。

### 11.6 正文质量不能只用一致性衡量

试写和改稿还应评估作者要求的人称、视角、语气、节奏、人物动机、情绪推进与表达辨识度。优先参考作者指定的范文、当前稿件和有适用范围的偏好，而不是套用统一的“小说腔”。

润色应保留作者有意采用的措辞、留白和叙述安排；不以增加形容词、拉长篇幅、补齐解释或消除所有歧义作为默认优化。跨多轮改稿应防止重复铺陈、情节回退和风格漂移。

## 12. 正文编辑、版本与并发

- 每次生成或修改绑定目标文档、基础版本、分支和适用范围。
- 当前未保存工作稿属于本轮真实输入，不以最近提交版本替代。
- 局部修改使用编辑器可验证的稳定定位与基础版本，不仅依赖易漂移的字符偏移。
- 非目标段落和作者要求保留的内容，不因润色、重试或模型输出整篇文本而被替换。
- 作者在生成期间继续编辑时，结果只能在验证可安全应用后合并；否则保留为待合并版本。
- 正式提交后仍保留修订；撤销已提交的关联变更需要检查后续依赖，不能粗暴回滚他人或作者后来的编辑。
- 停止生成应阻止后续自动应用；可能存在的计费和已经完成的持久化操作应如实呈现。
- 不完整结果明确标记，支持恢复或保留，但不能自动成为正式稿件。
- 支持网络失败、进程重启和切换项目后的恢复；重试具有幂等性，不重复应用。
- 网络超时而提交状态未知时，先查询持久化执行结果，再决定重试；不能把未收到响应当作未提交。

### 12.1 作者手动编辑与讨论状态同步

手动编辑的稿件是后续创作的真实输入，但并不自动将每一处改动提升为全书设定或长期偏好。系统应识别影响当前连续写作的变化，必要时提示它与讨论决定的差异。

原稿中的来源标记、AI 生成说明或旧采用状态不能覆盖后续作者编辑。采纳前展示的差异若已过期，需要重新计算；确认不能授权覆盖作者尚未看过的新差异。

## 13. 分支与关联变更

### 13.1 分支隔离

允许不同代价、人物动机或剧情走向分别试写。每个分支拥有明确的继承起点、局部决定和工作稿。

未采用分支不改变其他分支与正式设定。分支采用、局部合并和放弃均应保留可追溯关系，不把不同版本的规则拼成一套。

首个版本必须具备分支隔离和基本版本比较；复杂可视化版本树可以后续实现。

### 13.2 正式变更集

关联更新至少记录目标、基础版本、修改前后内容、来源、作者授权和执行状态。

同一数据库中可事务提交的正式关联修改必须整体成功或整体回滚。涉及索引等派生数据时，原始提交持久化后可重建派生结果，并清楚标记更新状态，不假装所有后续任务已经完成。

### 13.3 影响待办

设定大改后，检索受影响的角色、正文、关系、事件和伏笔，区分已确认影响与需要复查的疑点。

待办可以标记待处理、已处理、不适用或接受保留差异，并保留原因。没有完成全范围检查时，只报告已检查范围。

### 13.4 部分采用的语义

只采用某个段落，不等于采用整份回复中的所有建议、设定和推测；编辑操作、决定记录与正式提交都必须指向实际采用范围。

如果采用段落依赖尚未采用的新规则，应把依赖作为待确认项说明，而不是自动补交全部设定。整组变更允许先缩小为作者选择的子集，但执行前必须检查该子集是否自洽，再对这组明确的正式变更保持事务一致性。

## 14. 技术组织建议

以下是职责划分建议，允许在详细设计中调整，不要求一项对应一个新服务或类。

| 职责 | 负责内容 |
| --- | --- |
| 共创运行编排 | 意图、工具闭环、生成、取消、预算和结果状态 |
| 项目知识读取 | 当前有效资料、证据定位、关系和权限边界 |
| 检索与索引 | 增量更新、召回、排序、覆盖记录和缓存失效 |
| 决定与方案管理 | 选择、否定、替代、范围、分支和纠正 |
| 工作稿编辑 | 稳定定位、版本、流式结果、局部修改和冲突合并 |
| 正式变更执行 | 授权、版本检查、事务、幂等和影响待办 |
| 模型适配 | 真实工具调用、流式输出、结构校验及能力声明 |
| 共创工作区界面 | 讨论与稿件联动、来源、差异、恢复和确认 |

产品规则应能独立于某一模型提示词进行测试。禁止让前端直接相信模型给出的项目 ID、版本或写权限；模型提出的操作必须经过执行层验证。

讨论和正文共创共享知识与决定，但不要求复用现有正文生成的所有约束提示。应避免为统一而把两种任务塞入一个无法区分行为的巨大提示词。

### 14.1 输出校验与故障降级

模型返回的操作需要校验结构、对象类型、目标身份、基础版本、保护范围和授权状态。无法可靠解析或定位时，只能保留为回复或待处理建议，不可用猜测出的字段执行写入。

修复无效输出应有次数和费用上限，不能无限请求模型“修正 JSON”。已通过校验的文字可保留，但必须明确尚未执行的操作，不能因为展示了草稿就声称修改成功。

工具不可用时可以继续提供明确受限的讨论或试写，不能伪装已经查证或提交。备用模型、重试和超时恢复仍须遵守同一版本、权限、隐私和幂等规则；能力不足时应如实提示，而不是为旧接口牺牲核心效果。

### 14.2 资料发送与隐私边界

“作者秘密不能成为角色知识”与“资料能否发送给外部模型”是两种不同边界，不能混为同一可见性字段。

- 检索、摘要、重排和生成所使用的服务都必须遵守项目的数据发送设置，不只约束最终聊天请求。
- API 密钥、令牌等凭证不得进入提示词、检索内容或诊断日志，仅在指定服务所需的认证链路中使用；运行日志默认保留必要元数据，原文级诊断需明确可控。
- 外部参考材料与其他项目内容不会因语义相关就自动成为本书事实；跨项目读取需要明确授权。
- 模型或服务切换不能自动扩大原本允许发送的资料范围。
- 作者不允许某类资料外发时，应说明限制，并提供可用的本地处理或不读取该资料的路径；不暗中绕过，也不把它解释为禁止创作。

## 15. 实施顺序

以完整创作闭环推进，不先做一个仍与写作割裂的新聊天模块。

| 阶段 | 主要交付 | 完成条件 |
| --- | --- | --- |
| A：基线与详细设计 | 真实场景样例、状态和权限设计、迁移方案、检索与编辑技术验证 | 证明新设计能支持边聊边写，不依赖旧流程凑合 |
| B：最小完整共创闭环 | 发现已有设定、选择方向、形成工作稿、试写正文、局部修改、确认采用 | 在同一工作区跑通第 5 节流程，含基本版本和来源 |
| C：长期可靠性 | 决定替代与否定、历史方案找回、增量检索、并发编辑和故障恢复 | 长对话、资料更新、手动编辑和重试不产生隐性覆盖 |
| D：重大修改与深入体验 | 基本分支比较、关联变更、影响待办及性能调优 | 体系重构可追踪、可确认，等待和费用符合约定预算 |
| E：迁移与旧链路收敛 | 新格式验证、迁移演练、旧入口和兼容代码清理 | 用户资料完整，新主流程不依赖旧实现运行 |

版本、权限、来源和数据安全不是后期补丁，必须从阶段 B 的第一条闭环开始存在。阶段 C、D 是深化与扩大覆盖，不代表此前可以允许越权、串分支或丢失编辑。

复杂版本树、多工作区同时协作和外部资料自动研究不是首版前置条件。不得通过砍掉正文联动、动态查证或最新决定记忆来换取表面上的快速上线。

### 15.1 阶段完成与上线门槛

完成代码或跑通一次演示不等于阶段完成。每阶段需对应可重复的验收场景、失败恢复结果和明确的未完成项；阶段 A 必须把第 17.2 节的基线、质量阈值和性能预算具体化，再进入扩大实施。

首次对实际项目开放正式写入前，必须验证版本冲突、跨目标隔离、撤销、取消、超时重试和迁移恢复。无法安全处理的情况应保留草稿并阻止正式提交。

至少用一个新建空白项目和一个迁移后的长篇项目完成完整共创验收；前者不得依赖完整规划，后者不得依赖删减历史或清空资料才能运行。迁移备份必须演练恢复，不能仅确认备份文件存在。

## 16. 数据迁移与旧能力处理

1. 在项目副本上盘点消息、正文、修订、设定、来源关系和未采用候选。
2. 设计新格式，不以保留旧表字段和旧接口为前提。
3. 制作迁移前备份，记录格式版本、数量及可验证的内容完整性信息。
4. 能无损映射的数据迁入新结构；不能可靠判断的内容以原始记录或待核对资料保留。
5. 旧 AI 发言、旧摘要和模糊作者表达，不在迁移中被自动升级成已确认决定。
6. 校验原文、来源、修订、秘密可见性、项目归属和候选状态。
7. 迁移可重复验证，失败保留原项目；不要求在已经发生新格式编辑后用旧程序继续写入。
8. 新链路验收后收敛旧入口，避免长期双写、双解释和隐性数据分叉。

任何实际删除、不可逆转换或对原项目的覆盖，都不由本文自动授权，实施时必须说明并取得必要确认。

## 17. 验收场景

以下是必须进入评测与测试设计的场景，不要求每一项都通过同一种测试技术验证。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 已有境界体系，作者要求设计新境界 | 找到相关有效设定，说明要点，按需要区分扩展与重构 |
| AC-02 | 作者用“修炼等级”询问“境界体系” | 不仅依赖精确同名才能发现资料 |
| AC-03 | 规则限制藏在长资料中后段 | 保留相关条件与例外，不只取开头导致错误建议 |
| AC-04 | 资料读取失败或索引待更新 | 不将失败报告成“本书没有这个设定” |
| AC-05 | 数十轮后代价从寿命改为记忆 | 后续使用最新有效决定，不复活被替代规则 |
| AC-06 | 作者否定某方案，后来继续询问 | 不重复推荐为既定方向；需要复议时说明其已被否定 |
| AC-07 | 作者说“换第二个” | 找回对应历史方案，不把 AI 建议误当正式决定 |
| AC-08 | 切换到无关主题 | 不持续携带旧主题的局部规则或人物信息 |
| AC-09 | “如果失忆”和“试写失忆版” | 不自动修改正式设定 |
| AC-10 | 已有信息不足，但作者要求先写 | 可以合理创造，明确关键假设，不要求补齐表单 |
| AC-11 | 同一讨论从设定转入正文 | 正文沿用当前分支决定，稿件在同一工作区持续编辑 |
| AC-12 | “保留前半段，只改结尾” | 非目标内容不被改写，差异可核对 |
| AC-13 | AI 生成期间作者手动编辑 | 不覆盖新编辑；不能合并时保留为待处理结果 |
| AC-14 | 生成期间切换项目或稿件 | 结果不应用到错误目标 |
| AC-15 | 停止、断网、重试、应用重启 | 输入和已有稿件可恢复，不重复正式提交 |
| AC-16 | 同时探索寿命版与失忆版 | 分支独立，未采用内容不污染其他版本 |
| AC-17 | 修改体系并采用关联正文 | 变更范围可见，版本冲突时不部分覆盖正式对象 |
| AC-18 | 设定变化影响旧章节与伏笔 | 形成有来源的影响待办，不声称已经全书修复 |
| AC-19 | 早期不会御剑，后期学会 | 根据故事时间判断，不误报矛盾 |
| AC-20 | 作者秘密、角色误解与不可靠叙述 | 不让角色全知，不把谎言直接纠正成客观真相 |
| AC-21 | 作者要求找出全部相关章节 | 分批查找，展示覆盖，未完成时不宣称查全 |
| AC-22 | 正文或设定修改后立即再询问 | 使用当前版本，过期缓存和摘要不覆盖新内容 |
| AC-23 | 删除或纠正局部写作偏好 | 后续不继续使用失效记忆，不扩大偏好作用范围 |
| AC-24 | 无关资料持续增长 | 相关检索质量和等待保持在约定指标内，不每轮读取全书 |
| AC-25 | 项目文本包含要求扩大权限的内容 | 不将其作为系统指令执行，不越权读写其他目标 |
| AC-26 | 旧项目迁移 | 原始创作资料可核对，模糊记录不被升级成正式事实 |
| AC-27 | 写早期章节，但已有后期能力和真相 | 尊重当前叙事位置、视角与揭示安排，不因误用后期资料擅自提前赋予能力或揭露秘密 |
| AC-28 | 正文证据改写或规则撤回 | 派生事实与摘要进入失效或待核对状态，不继续作为有效依据 |
| AC-29 | 删除错误记忆后再次检索旧消息 | 不自动重建同一已撤回记忆 |
| AC-30 | 生成中补充“结尾不要死人” | 旧任务不再自动应用，新指令被正确承接且费用变化可见 |
| AC-31 | 仅采用回复中的一个段落 | 不采用其余建议；依赖未确认规则时明确提示 |
| AC-32 | 超时发生在正式变更已经提交之后 | 查询实际状态，不因重试重复写入或误报未提交 |
| AC-33 | 修改实体名称或出现同名角色 | 引用仍指向正确稳定身份，同名对象不被合并 |
| AC-34 | 检索命中被预算裁剪，未送入模型 | 不将其展示为模型已经读过或使用的证据 |
| AC-35 | 工具失败、输出操作无效或切换备用模型 | 不假查证、不猜测写入、不扩大权限和资料发送范围 |
| AC-36 | 连续润色同一章节并参考作者范文 | 保留指定表达与节奏，不重复铺陈、回退情节或擅改视角 |
| AC-37 | 长任务分段执行后中断，期间作者修改稿件 | 恢复时核对最新版本与决定，不仅凭旧摘要继续覆盖 |
| AC-38 | 外发限制与模型或检索服务切换 | 所有相关调用遵守同一发送边界，日志不泄露凭证 |
| AC-39 | 作者手动编辑后，旧差异仍在等待确认 | 重算实际差异，不借旧确认覆盖未展示的新内容 |
| AC-40 | 新建空白项目与迁移后的长篇项目 | 都能完成共创闭环；备份可恢复，不依赖填表或清空历史 |

### 17.1 评测方法

- 确定性单元与集成测试覆盖状态、权限、版本、事务、索引失效和幂等。
- 浏览器交互测试覆盖讨论与稿件联动、窄屏、停止、恢复、局部采用和并发编辑。
- 模拟模型与固定输出可验证执行边界，但不能证明真实模型会发现设定或理解指代。
- 真实模型小规模评测验证检索选择、语义召回、决定理解、创作质量和冲突判断；费用受控，单独获得运行授权。
- 人工评阅使用固定场景与评价尺度，保留失败样例，禁止只展示最顺畅的一次结果。
- 比较旧实现与新实现的同一组案例；核心样例必须有改善证据，不能只凭提示词和架构图宣称提升。

### 17.2 性能与质量指标

阶段 A 必须建立基线，并在选择实际模型和测试设备后填入数值目标。没有基线与测量环境，不在本文虚构绝对速度承诺。

至少记录：

- 冷、热索引下的检索耗时，以及普通讨论、局部改写、全面查证的端到端 P50/P95。
- 首个有用结果的等待时间，区分状态提示、讨论文字和实际稿件内容。
- 每轮输入与输出 token、工具轮次、模型请求次数和费用。
- 随章节、设定和历史消息数量增长时的读取量与耗时变化。
- 相关资料召回、无关资料混入、引用准确性、检索覆盖与错误“不存在”判断。
- 最新决定遵从、废弃方案复活、串分支、非目标改写和错误覆盖。
- 作者完成同一任务所需的复制、切换、确认和手工维护步骤。
- 正文的人称与视角、人物动机、情绪推进、作者风格保留和跨轮次重复程度。
- 原始依据变化到派生内容失效的延迟，以及在此期间错误使用旧结论的次数。

目标应同时约束创作效果和资源投入。数据安全、越权、错误目标写入和静默覆盖属于阻断性缺陷，不能用平均体验评分抵消。

## 18. 实施前待定事项

以下事项需要验证后落定，不改变已经确认的产品方向：

1. 检索的关键词、语义、关系扩展和排序组合，以及是否需要额外服务。
2. 模型工具调用、流式编辑、结构化输出和取消机制的实际支持情况。
3. 稿件稳定定位、局部应用、版本分叉与冲突合并的具体方案。
4. 新数据模型、索引更新机制、迁移版本和旧格式只读保留方式。
5. 常规与深入任务的预算、超预算确认方式和性能数值。
6. 正式采用的界面确认语义、局部采用交互及一次确认覆盖的变更范围。
7. 故事位置与角色知情范围的表达方式，以及资料变化后的依赖失效机制。
8. 生成中补充指令的调度语义、任务检查点和跨步骤快照验证方式。
9. 各类服务的数据发送策略、诊断保留范围和备用模型的能力门槛。

这些事项不能成为重新引入旧流程限制的理由。方案选择以标准场景效果、验证结果、复杂度和长期维护成本为依据。

## 19. 最终决策摘要

- 已决定全面重构讨论，并将设定、大纲和正文共创统一纳入主工作流。
- 效果优先，允许破坏旧接口、重做数据模型与交互，不为兼容牺牲目标体验。
- AI 可以自主查证、自由发散和直接参与工作稿创作，但不能把建议冒充依据或越权提交。
- 系统维护有来源、有范围、可纠正的决定记忆，支持版本、基本分支及关联变更。
- 共创效果同时包含叙事质量与一致性；叙事位置、部分采用和依据失效必须进入执行与验收规则。
- 以完整的边聊边写闭环和真实创作场景验收，不以页面改版或提示词调整代替重构。
- 保护作者资产是底线，不是必须保留旧架构的理由。
